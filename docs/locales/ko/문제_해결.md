# 문제 해결

> **표준 영어 소스:** [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md). 이 현지화된 문서는 정확한 명령, 경로, 키, 상태 값, 해시 및 파일 이름을 보존합니다. 기술적인 표현이 다를 경우 영어 소스를 사용하세요.


Guard가 로드되지 않거나, 소스를 수집할 수 없거나, 보고서가 나타나지 않거나, 경로 증명이 예상한 것과 모순되는 경우 이 페이지를 사용하십시오. 의사결정 트리에서 시작하여 하나의 분기를 따릅니다. 전용 [상태 및 오류 참조](%EC%83%81%ED%83%9C_%EB%B0%8F_%EC%98%A4%EB%A5%98_%EC%B0%B8%EC%A1%B0.md)실패한 레이어가 알려진 후에만.

구성을 변경하거나 다시 설치하기 전에 현재 런타임 파일을 보존하세요. 오래되었거나 누락된 아티팩트는 실패한 단계를 식별합니다. 반복적으로 다시 시작하면 해당 증거가 지워질 수 있습니다.

<a id="choose-the-failure-path"></a>
## 실패 경로 선택

<a id="1-decide-whether-guard-loaded"></a>
### 1. Guard가 로드되었는지 여부를 결정합니다

- **없음 `runtime/` 파일이 존재하지 않습니다.** 따르세요 [누락된 런타임 파일을 복원하세요.](#restore-missing-runtime-files). 설치 경로, 표준 로더, `enabled.txt` 및 `mods.txt`를 확인하세요.
- **현재 상태 파일이 있는지 확인하세요.** Guard가 상태를 쓸 수 있을 만큼 충분히 로드되었습니다. 2단계로 계속 진행하세요. 재설치가 첫 번째 응답이 아닙니다.

<a id="2-decide-whether-the-scheduler-is-advancing"></a>
### 2. 스케줄러가 진행 중인지 결정합니다.

열기:

```text
runtime/current/startup_status.json
runtime/current/poll_status.json
```

- **카운터 및 타임스탬프 진행:** 3단계로 계속 진행합니다.
- **`poll_id` 정적입니다. `poll_in_flight` true로 유지되거나 스케줄러 상태가 실행되지 않습니다.** 따르세요 [멈춘 폴링 루프를 복구하고](#recover-a-stuck-poll-loop).
- **스케줄러 진행이 계속되는 동안 기준 스캔이 보류 중입니다.** 이는 주의 사항이지 자동이 아닙니다. 시동 실패. 백로그 또는 스캔 진행이 중지된 경우에만 조사하십시오.

<a id="3-classify-route-proof"></a>
### 3. 경로 증명을 분류

열기`runtime/final_logs/route_proof.json`하고 모든 경로를 검사하십시오. 별도로.

- **`full`:** 예상치 못한 표현을 현재와 비교 `source_references` 및 계보와 비교하세요. 문구만으로는 잘못된 것처럼 보이므로 전달을 변경하지 마세요.
- **`limited_expected_empty`:** 소스 계정이 합법적인 빈 결과를 지원하는지 확인하세요. 합성 플레이어나 케이스를 생성하지 마세요.
- **`missing`:** 따르세요 [누락된 경로를 진단하고](#diagnose-a-missing-route).

<a id="4-classify-source-coverage"></a>
### 4. 소스 적용 범위 분류

- **`partial`, `deferred`, `unavailable`, `malformed`, `permission_denied` 또는 `error`:** 따르세요 [불완전한 소스 적용 범위를 해석](#interpret-incomplete-source-coverage)그런 다음 [상태 및 오류 참조](%EC%83%81%ED%83%9C_%EB%B0%8F_%EC%98%A4%EB%A5%98_%EC%B0%B8%EC%A1%B0.md).
- **구조화된 소스는 최신이지만 번역되었거나 보류 중인 출력이 더 오래되었습니다.** 전달 엔드포인트가 아닌 완료 핸드오프를 진단합니다. 전송 구성을 변경하기 전에 타임스탬프를 모두 보존하고 보고서 및 발송 상태를 검사하세요.

<a id="5-follow-the-matching-branch"></a>
### 5. 일치하는 분기를 따릅니다

- 불완전한 신원: [매핑되지 않은 플레이어 매핑](#map-an-unmapped-player).
- 일일 연속성 누락: [누락된 일일 롤업 복원](#restore-a-missing-daily-rollup).
- 명시적으로 승인된 시행 테스트가 작성되지 않았습니다: [차단된 Admin.ini 쓰기](#diagnose-a-blocked-adminini-write).
- ZIP 추출 실패: [해결 방법 Windows 추출 케이스 충돌](#resolve-a-windows-extraction-folder-collision).
- 픽스, 패키지 또는 저장소 확인 실패: [검증 및 출시 검토](%EA%B2%80%EC%A6%9D_%EB%B0%8F_%EB%A6%B4%EB%A6%AC%EC%8A%A4.md#avoid-validation-environment-pitfalls).

<a id="6-stop-with-one-proved-outcome"></a>
### 6. 하나의 입증된 결과로 중지

문제 해결 단계가 종료됩니다. 언제:

- 경로가 현재이고 `full`;
- 경로가 현재이고 `limited_expected_empty`명명된 이유로 인해;
- 하나의 정확한 차단 장치, 증거 경로 및 다음 조치가 기록됩니다.
- 롤백은 이전에 알려진 상태를 복원하고 실패한 증거를 보존했습니다.

“서버가 실행 중입니다.” 하트 비트가 증가하거나 HTTP 성공만으로는 보고 경로가 완료되었음을 증명할 수 없습니다.

<a id="diagnose-a-missing-route"></a>
## 누락된 경로를 진단하고

열기`runtime/final_logs/route_proof.json` 비교 `server_status`, `daily_rollup`, `player_activity`, `case_review` 및 `critical_guard`.

1. 경로의 이유, 계보, 생성 시간 및 소스 참조.
2. 이름이 지정된 구조화된 소스가 존재하고 동일한 주기에 속하는지 확인하세요.
3. 해당 mtime을 번역된 출력 및 보류 중인 봉투와 비교하세요.
4. 최종 로그가 번역되었거나 보류 중인 출력보다 최신인 경우 오래된 완료 디스패치를 기록하고 해당 핸드오프를 먼저 복구하세요.
5. 모든 로컬 출력이 최신이지만 전달이 없는 경우 경로를 검사하세요. 구성 및 발신자 상태.

5 경로 증명에 대한 스케줄러 상태 또는 하나의 성공적인 알림을 승격하지 마십시오.

<a id="interpret-incomplete-source-coverage"></a>
## 불완전한 소스 적용 범위를 해석

| 상태 | 해야 할 일 |
|---|---|
| `partial` | 수집된 증거만 사용하고 완전한 적용 범위 주장을 피하십시오. |
| `deferred` | 나중에 제한된 작업 진행을 먼저 확인하세요. 구성을 변경합니다. |
| `unavailable` | 환경 제한을 기록합니다. 입증된 경로나 권한 문제만 수정하세요. |
| `malformed` | 소스와 구문 분석 오류를 보존하세요. 누락된 값을 추측하지 마십시오. |
| `permission_denied` | 필요한 제한된 읽기 권한만 부여하십시오. |
| `error` | 경로에 의존하기 전에 세부정보를 보존하고 명명된 단계를 진단하십시오. |

<a id="restore-missing-runtime-files"></a>
## 누락된 런타임 파일을 복원하세요.

확인:

```text
mods.txt contains RandomDayGuard : 1
RandomDayGuard/enabled.txt exists
RandomDayGuard/Scripts/main.lua exists
```

올바른 설치 루트는 다음과 같습니다.

```text
AbioticFactor/Binaries/Win64/ue4ss/Mods/RandomDayGuard/
```

이 중첩 레이아웃 거부:

```text
Mods/RandomDayGuard/RandomDayGuard/Scripts/main.lua
```

파일이 정확하지만 UE4SS Guard를 시작하지 않은 경우 `UE4SS.log` 시작 타임스탬프를 실제 게임 프로세스 시작과 비교하세요.

<a id="resolve-a-windows-extraction-folder-collision"></a>
## Windows 추출 폴더 충돌 해결

이전 릴리스에서는 이름이 대문자로만 다른 프로그램 디렉토리를 사용했습니다. 일부 Windows 추출기는 ZIP가 기존 폴더 위에 배치될 때 해당 이름을 병합합니다.

1. 실패한 임시 추출만 삭제하고 설치된 모드나 그 증거는 삭제하지 마세요.
2. 빈 임시 디렉터리를 새로 만듭니다.
3. 여기에서 현재 릴리스를 추출하세요.
4. 하나의 RandomDayGuard 폴더와 하나의 프로그램 디렉토리가 생성되는지 확인하세요.
5. Windows에서 여전히 충돌이 보고되면 릴리스를 다시 다운로드하고 사용된 릴리스 버전과 추출기를 보고하세요.

설치된 폴더에 새 릴리스를 추출하지 마십시오. [`../INSTALL.md`](%EC%84%A4%EC%B9%98.md).

## 예상 버전 로드

소스 마커 및 빌드 마커 확인:

```sh

```

동의하지 않는 경우:

2. 설치된 폴더, 검토된 구성, 런타임 증거를 백업하세요.
3. 의도한 패키지를 스테이징하고 검사합니다.
4. 패키지 관리 프로그램과 데이터 파일만 교체하세요.
5. 표준 로더가 존재하고 소문자 중복이 추가되지 않았는지 확인하세요.
6. 한 번 시작하고 런타임 출력을 판단하기 전에 현재 마커를 다시 읽어보세요.

<a id="recover-a-stalled-historical-scan"></a>
## 중단된 기록 스캔 복구

현재 모니터링과 기록 검색은 별개입니다. 대규모 아카이브에는 제한된 주기가 많이 필요할 수 있으므로 변경되지 않은 하나의 관찰만으로는 정지되었다고 할 수 없습니다.

1. 열기`runtime/current/report_worker_status.json`.
2. 기록 `scan_cursor`, 발견된 파일, 완료된 파일 및 `last_progress_ts`.
3. 최소 2번의 일반 보고 작업자 기회를 기다린 후 동일한 필드를 다시 비교하세요.
4. 커서, 완료 횟수 또는 진행 시간이 빨라지면 스캔이 계속 작동하는 것입니다. 제한된 상태로 두세요.
5. 설문 ID 및 현재 보고서가 계속 진행되는 동안 모든 진행률 필드가 변경되지 않은 경우 상태 파일을 보존하고 작업자 단계에서 명명한 소스 클래스를 확인하세요. 재시도하기 전에 해당 소스 경로를 복구하거나 읽기 오류를 읽으십시오.

중단된 기록 스캔은 오래된 기록이 필요한 결론을 제한합니다. 활성 로그 및 현재 주기 증명이 최신인 현재 보고서를 무효화하지 않습니다.

<a id="recover-a-stuck-poll-loop"></a>
## 멈춘 폴링 루프를 복구하고

열기:

```text
runtime/current/poll_status.json
runtime/poll_error.txt
```

기록 `poll_id`, `poll_completed_count`, `poll_in_flight`, `poll_stage`, `scheduler_status`제한된 간격으로 타임스탬프를 두 번 표시합니다.

- 카운터가 진행되면 루프가 멈추지 않습니다. 이후 작업자 단계를 진단합니다.
- `poll_in_flight=true`변경되지 않고 다시 시작하기 전에 마지막 진행 단계와 오류를 보존합니다.
- 스케줄러가 중지된 경우 이전 오류 및 시작 핸드오프를 검사합니다.

중단된 수명 주기를 보상하기 위해 두 번째 루프 소유자를 추가하지 마세요.

<a id="start-the-scan-after-log-backlog"></a>
## 로그 백로그 후에 검색을 시작하세요

`runtime/current/poll_status.json`에서 비교:

```text

active_log_unread_bytes
log_backlog_pending
```

기록 검색은 활성 로그에 읽지 않은 바이트가 있는 동안 기다려야 합니다. 나중에 여론 조사를 통해 백로그가 줄어드는지 확인하세요. 폴링 진행 시 읽지 않은 고정 개수는 소스 테일 문제입니다. 고정된 폴링은 스케줄러 문제입니다.

<a id="diagnose-a-blocked-adminini-write"></a>
## 차단된 Admin.ini 쓰기

실시간 서버 파일이 아닌 명시적인 승인과 일회용 테스트 파일을 통해서만 시행 테스트를 실행하세요. 먼저 테스트 구성에서 Guard에게 다음을 작성하도록 요청하는지 확인하세요.

```lua
review_only_mode = false
auto_ban = true
write_admin_ini = true
```

그런 다음 기록된 실패 이유를 읽어보세요. Guard는 하나의 계정을 식별하고, 중재자와 신뢰할 수 있는 계정을 보호하고, 충분한 계정 관련 증거를 찾고, 새 백업을 생성 및 확인하고, 다른 프로그램이 파일을 변경하지 않았는지 확인하고, 의도한 업데이트를 저장하고, 저장된 파일 전체를 의도한 결과와 비교해야 합니다. 단계가 실패하거나 확인할 수 없는 경우 금지 목록을 변경하지 않고 그대로 두세요. 참조 [Admin.ini 시행](%EA%B4%80%EB%A6%AC%EC%9E%90_INI_%EC%8B%9C%ED%96%89.md).

<a id="restore-a-missing-daily-rollup"></a>
## 누락된 일일 롤업 복원

확인 `forensic_rollup.enabled = true`을 참조한 후 검사:

```text
runtime/current/forensic_today.json
runtime/forensic_days/YYYY-MM-DD/
runtime/final_logs/YYYY-MM-DD/
```

이러한 항목이 누락된 경우 시작, 폴링, 보고 작업자 및 소스 계정 상태를 순서대로 확인하세요. 일일 롤업은 반복되는 서버 상태 알림이 아닌 하루에 하나의 연속성 기록입니다.
