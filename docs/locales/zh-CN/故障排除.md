# 故障排除

> **规范的英文来源:** [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md). 此本地化文档保留了准确的命令、路径、键、状态值、哈希值和文件名。如果技术措辞不同，请使用英文来源。


当 Guard 未加载、无法收集源、报告未出现或路线证明与您的预期相矛盾时，请使用此页面。从决策树开始并遵循一个分支。 Use the dedicated [状态和错误参考](%E7%8A%B6%E6%80%81%E5%92%8C%E9%94%99%E8%AF%AF%E5%8F%82%E8%80%83.md)仅在知道失败的层后。

在更改配置或重新安装之前保留当前运行时文件。陈旧或丢失的工件标识失败的阶段；重复重新启动可能会消除该证据。

<a id="choose-the-failure-path"></a>
## 选择失败路径

<a id="1-decide-whether-guard-loaded"></a>
### 1.确定 Guard 是否加载

- **不存在`runtime/`文件：**遵循[恢复丢失的运行时文件](#restore-missing-runtime-files)。 Verify install path, canonical loader, `enabled.txt` 一致，并且 `mods.txt`。
- **Current status files exist:** Guard loaded far enough to write state.继续步骤2；重新安装不是第一个响应。

<a id="2-decide-whether-the-scheduler-is-advancing"></a>
### 2.决定调度程序是否提前

打开：

```text
runtime/current/startup_status.json
runtime/current/poll_status.json
```

- **计数器和时间戳提前：**继续执行步骤 3。
- **`poll_id` 是静态的，`poll_in_flight`保持 true，或者调度程序状态未运行：**遵循[恢复卡住的轮询循环](#recover-a-stuck-poll-loop).
- **基线扫描待处理，而调度程序进度继续：**这是一个警告，不会自动失败 startup.仅在积压或扫描进度停止时进行调查。

<a id="3-classify-route-proof"></a>
### 3. 对路由证明进行分类

打开`runtime/final_logs/route_proof.json` 并检查每条路由分别。

- **`full`:**将意外措辞与当前`source_references` 和谱系进行比较。不要更改交付，因为措辞本身看起来就有问题。
- **`limited_expected_empty`:**进行比较，确认源会计支持合法的空结果。不要创建合成播放器或案例。
- **`missing`:**遵循[诊断丢失的路由](#diagnose-a-missing-route).

<a id="4-classify-source-coverage"></a>
### 4. 对源覆盖范围进行分类

- **`partial`, `deferred`, `unavailable`, `malformed`, `permission_denied`，或`error`:**遵循[解释不完整的源覆盖范围](#interpret-incomplete-source-coverage)，然后在 [状态和错误参考](%E7%8A%B6%E6%80%81%E5%92%8C%E9%94%99%E8%AF%AF%E5%8F%82%E8%80%83.md).
- **结构化源是最新的，但翻译或待处理的输出较旧：**诊断完成切换中查找确切的代码，而不是交付端点。在更改交付配置之前保留时间戳并检查报告和调度状态。

<a id="5-follow-the-matching-branch"></a>
### 5. 遵循匹配分支

- 身份不完整：[映射未映射的玩家](#map-an-unmapped-player).
- 缺少日常连续性：[恢复丢失的每日汇总](#restore-a-missing-daily-rollup).
- 明确批准的执行测试未写入：[诊断被阻止的Admin.ini写入](#diagnose-a-blocked-adminini-write).
- ZIP提取失败：[解决 Windows 提取案例 collision](#resolve-a-windows-extraction-folder-collision).
- Fixture, package, or repository check failed: [验证和发布审核](%E9%AA%8C%E8%AF%81%E5%92%8C%E5%8F%91%E5%B8%83.md#avoid-validation-environment-pitfalls).

<a id="6-stop-with-one-proved-outcome"></a>
### 6. 以一个经过验证的结果停止

故障排除过程在以下情况下结束：

- 路线是当前的，`full`;
- 路线是当前的，`limited_expected_empty`出于指定原因；
- 记录了一个确切的拦截器、证据路径和下一步操作；或者
- 回滚恢复之前已知的状态并保留失败的证据。

“服务器正在运行”、心跳增加或HTTP仅成功并不能证明报告路由已完成。

<a id="diagnose-a-missing-route"></a>
## 诊断丢失的路由

打开`runtime/final_logs/route_proof.json`并比较`server_status`, `daily_rollup`, `player_activity`, `case_review` 一致，并且 `critical_guard`.

1. 读取路由的原因、沿袭、生成时间和源引用。
2. 确认指定的结构化源存在并且属于同一周期。
3. 将其 mtime 与已翻译的输出和待处理的信封进行比较。
4. 如果最终日志比已翻译或待处理的输出更新，则首先记录陈旧的完成分派并修复该移交。
5. 如果所有本地输出都是最新的但未交付，则检查路由配置和发件人状态。

不要宣传调度程序运行状况或一次成功的五路由证明通知。

<a id="interpret-incomplete-source-coverage"></a>
## 解释不完整的源覆盖范围

| 状态 | 该做什么 |
|---|---|
| `partial` | 仅使用收集到的证据，避免完全覆盖声明。 |
| `deferred` | 在更改之前确认后续有限的工作进度配置。 |
| `unavailable` | 记录环境限制；仅更正经过验证的路径或权限问题。 |
| `malformed` | 保留源和解析错误；不要猜测缺失值。 |
| `permission_denied` | 仅授予所需的窄读权限。 |
| `error` | 在依赖路由之前保留详细信息并诊断指定阶段。 |

<a id="restore-missing-runtime-files"></a>
## 恢复丢失的运行时文件

确认：

```text
mods.txt contains RandomDayGuard : 1
RandomDayGuard/enabled.txt exists
RandomDayGuard/Scripts/main.lua exists
```

正确的安装根目录是：

```text
AbioticFactor/Binaries/Win64/ue4ss/Mods/RandomDayGuard/
```

拒绝此嵌套布局：

```text
Mods/RandomDayGuard/RandomDayGuard/Scripts/main.lua
```

如果文件正确，但UE4SS未启动 Guard，请保留`UE4SS.log`并将其启动时间戳与实际游戏进程启动进行比较。

<a id="resolve-a-windows-extraction-folder-collision"></a>
## 解决 Windows 提取文件夹冲突

旧版本使用的程序目录的名称仅大小写不同。当 ZIP 放置在现有文件夹上时，某些 Windows 提取器会合并这些名称。

1. 仅删除不成功的临时提取，而不删除已安装的 mod 或其证据。
2. 创建一个新的空临时目录。
3. 在其中提取当前版本。
4. 确认它会生成一个 RandomDayGuard 文件夹和一个程序目录。
5. 如果 Windows 仍然报告冲突，请再次下载版本并报告版本和使用的提取程序。

Never extract a new release over the installed folder. Follow the clean-folder update procedure in [`../INSTALL.md`](%E5%AE%89%E8%A3%85.md).

<a id="load-the-expected-version"></a>
## 加载预期版本

检查源标记和构建标记：

```sh
grep -n "local VERSION" RandomDayGuard/Scripts/main.lua
cat RandomDayGuard/BUILD_MARKER.txt
```

如果他们不同意：

1. 停止服务器。
2. 备份已安装的文件夹、审查的配置和运行时证据中的干净文件夹更新过程。
3. 暂存并检查预期的包。
4. 仅替换包管理的程序和数据文件。
5. 确认规范加载程序存在并且未添加小写重复项。
6. 在判断运行时输出之前启动一次并读回当前标记。

<a id="correct-a-missing-saved-root"></a>
## 更正丢失的已保存根

打开`runtime/saved_path_probe.json`。将经过验证的绝对路径放入完整的Abiotic Factor`Saved/` 目录的完整路径放入 RandomDayGuard 文件夹内的 `SavedRoot.txt`；不要只指向世界目录。有界根之外的路径必须保持拒绝状态。

<a id="recover-a-stalled-historical-scan"></a>
## 恢复停止的历史扫描

当前监控和历史发现是分开的。大型存档可能需要许多有界循环，因此一次未更改的观察不足以将其称为停滞。

1. 打开`runtime/current/report_worker_status.json`.
2. 记录`scan_cursor`、发现文件、完成文件，以及`last_progress_ts`.
3. 等待至少两个正常的报告工作人员机会并再次比较相同的字段。
4. 如果光标、已完成计数或进度时间前进，则扫描仍在进行。保留其范围。
5. 如果在轮询 ID 和当前报告继续前进时所有进度字段保持不变，请保留状态文件并检查由工作阶段命名的源类。在重试之前修复该源路径或读取失败。

停滞的历史扫描限制了需要较旧记录的结论。它不会使活动日志和当前周期证明新鲜的当前报告无效。

<a id="recover-a-stuck-poll-loop"></a>
## 恢复卡住的轮询循环

打开：

```text
runtime/current/poll_status.json
runtime/poll_error.txt
```

记录`poll_id`, `poll_completed_count`, `poll_in_flight`, `poll_stage`, `scheduler_status`，并在有限的时间间隔内两次时间戳。

- 如果计数器前进，则循环不会卡住；诊断后面的工作阶段。
- 如果`poll_in_flight=true`保持不变，在重新启动之前保留最后的进度阶段和错误。
- 如果调度程序停止，请检查前面的错误和启动切换。

不要添加第二个循环所有者来补偿一个停滞的生命周期。

<a id="start-the-scan-after-log-backlog"></a>
## 在日志积压后开始扫描

在`runtime/current/poll_status.json`中，比较：

```text
active_log_caught_up
active_log_unread_bytes
log_backlog_pending
```

当活动日志有未读字节时，历史扫描应等待。确认稍后的民意调查减少了积压。随着民意调查的推进，固定的未读计数是一个源尾问题；固定轮询是调度程序问题。

<a id="preserve-scan-progress-after-a-crash"></a>
## 在崩溃后保留扫描进度

保留并比较：

```text
runtime/scan_checkpoint.json
runtime/scan_progress.json
runtime/baselines/file_manifest.tsv
```

检查检查点或清单是否丢失，保存的根或世界是否更改，或者检查点是否被标记为过时。请勿删除有效基线以使进度显得更新。

<a id="map-an-unmapped-player"></a>
## 映射未映射的玩家

将会话证据与权威日志进行比较：

```text
runtime/evidence/session_events.jsonl
Saved/Logs/AbioticFactor.log
```

查找显示名称之间的完整`Login request`关系，`ConnectID` 一致，并且 `UniqueId`。如果不存在接受的连接标识，则将该行保留为仅审阅状态。仅显示名称或 PlayerData 文件名并不是可执行的标识。

<a id="diagnose-a-blocked-adminini-write"></a>
## 诊断被阻止的Admin.ini写入

仅在明确批准和一次性测试文件的情况下运行强制测试，切勿使用实时服务器文件。首先确认测试配置要求Guard写入：

```lua
review_only_mode = false
auto_ban = true
write_admin_ini = true
```

Then read the recorded failure reason. Guard 必须识别一个帐户、保护管理员和受信任帐户、找到足够的特定于帐户的证据、创建并验证新备份、确认没有其他程序更改文件、保存预期更新，并将完整保存的文件与预期结果进行比较。如果任何步骤失败或无法检查，请保留禁止列表不变。 See [Admin.ini强制执行](%E7%AE%A1%E7%90%86%E5%91%98%E5%88%9D%E5%A7%8B%E5%8C%96%E6%89%A7%E8%A1%8C.md).

<a id="restore-a-missing-daily-rollup"></a>
## 恢复丢失的每日汇总

确认`forensic_rollup.enabled = true`，然后检查：

```text
runtime/current/forensic_today.json
runtime/forensic_days/YYYY-MM-DD/
runtime/final_logs/YYYY-MM-DD/
```

如果这些丢失，请按顺序检查启动、轮询、报告工作人员和源记帐状态。每日汇总是每天一个连续性记录，而不是重复的服务器状态通知。

## 查找确切的状态或错误
