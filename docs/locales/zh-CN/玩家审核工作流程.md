# 玩家审核工作流程

> **规范的英文来源:** [PLAYER_REVIEW_WORKFLOW.md](../../PLAYER_REVIEW_WORKFLOW.md). 此本地化文档保留了准确的命令、路径、键、状态值、哈希值和文件名。如果技术措辞不同，请使用英文来源。


将此页面用于一个玩家、帐户或案例。目的是可重复的审查决定，而不是自动指控。

<a id="quick-path"></a>
## 快速路径

1. 打开`runtime/final_logs/player_activity_latest.json`.
2. 确认路由状态`runtime/final_logs/route_proof.json`.
3. 确定哪些观察是当前的，哪些是历史的。
4. 检查引用的身份和会话来源引用。
5. 在推理之前查看`case_review_latest.json`当存在相关案例时。
6. 记录未知数，`does_not_prove`在选择操作之前。
7. 保持禁用强制执行，除非单独执行门已被证明。

<a id="1-confirm-route-proof"></a>
## 1.确认路线证明

将玩家路线解释为：

| 状态 | 操作 |
|---|---|
| `full` | 继续，同时仍然检查源限制。 |
| `limited_expected_empty` | 仅对实际存在的对象继续；不要发明失踪的玩家或案例。 |
| `missing` | 停止玩家决策并对路线进行故障排除。 |

健康的调度程序不会取代路线证明。

<a id="2-establish-identity"></a>
## 2.建立身份

首选由服务器公开的身份证据和文件名（如果有）证实的干净帐户标识符。PlayerData 文件名。保留原始来源参考。

不要强制执行：

- 单独的显示名称；
- 在通知或托管面板中看到的名称；
- 时间相似性；
- 未映射或弱信任身份；
- 没有当前证实的历史报告。

<a id="3-separate-current-from-historical"></a>
## 3.将当前与历史分开

当前证据描述了活动报告窗口或服务器纪元。历史证据可以解释某种模式，但它不能默默地填补当前窗口中的空白。

独立记录两个范围：

```text
Current observations:
Current source references:
Historical context:
Historical source references:
```

<a id="4-review-observations-and-interpretation"></a>
## 4.回顾观察和解释

清楚地阅读这些报告部分：

```text
observed
interpretation
unknown
does_not_prove
next_action
source_references
```

重新打开引用的结构化证据以做出任何重大决定。翻译是导航和解释，而不是新证据。

<a id="5-calibrate-the-decision"></a>
## 5。校准决策

| 决定 | 何时使用 |
|---|---|
| `INFO` | 正常或低上下文观察。 |
| `WATCH` | 值得监控的弱或不完整信号。 |
| `REVIEW` | 相关证据需要管理员判断。 |
| `BAN-ELIGIBLE` | 满足干净身份和配置的证据阈值；写门仍然适用。 |
| `AUTO-BANNED` | 已明确启用强制执行，并且备份、写入、读回和审核均成功。 |

没有任何决策标签可以证明有罪或意图。

<a id="6-apply-the-evidence-boundary"></a>
## 6.应用证据边界

崩溃、重新连接、警告，object/class 令牌和案例分组可以支持审核。单独而言，它们并不能证明作弊、盗窃、复制、所有权、直接损害或事件因果关系。

如果身份、解析、备份、写入、读回或回滚很弱或失败，则强制执行必须失败关闭。
