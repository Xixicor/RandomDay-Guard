# 从这里开始：阅读第一份 Guard 报告

> **规范的英文来源:** [START_HERE.md](../../START_HERE.md). 此本地化文档保留了准确的命令、路径、键、状态值、哈希值和文件名。如果技术措辞不同，请使用英文来源。


本指南在安装并启用 RandomDayGuard 后开始。它证明了一个有用的结果，无需要求新操作员检查源代码、包内部结构或仅限机器的状态文件。

<a id="what-happens-after-the-server-starts"></a>
## 服务器启动后会发生什么

Guard 等待游戏服务器并UE4SS加载，查找服务器的可用记录，并启动有界后台扫描。它可以报告当前服务器的运行状况，同时仍在对较旧的历史记录进行索引。

生成 第一份报告应为 **服务器状态**。它回答 Guard 现在是否正在完成监控周期、当前服务器运行何时开始（如果该时间戳可用）、技术记录多少active/rotated 日志和扫描覆盖范围、连接了多少个玩家、缺少哪些源组以及是否需要操作员操作。

仍在进行的后台扫描是对历史覆盖范围的限制，不会自动导致启动失败。 Guard 记录扫描光标、已完成的文件、发现的文件以及上次进度时间。如果这些值在重复的监视周期中停止变化，请将历史路径视为已停止并遵循故障排除中的扫描分支。不要仅仅因为旧历史记录不完整而丢弃当前日志和会话结果。

<a id="read-the-first-server-status-report"></a>
## 阅读第一个服务器状态报告

1. 正常启动专用服务器。
2. 等待游戏服务器并UE4SS完成启动。
3. 打开RandomDayGuard's 最终报告文件夹并选择最新的可读服务器状态报告。
4. 确认报告包含：
   - **Summary**
   - **What Guard observed**
   - **What it means**
   - **What remains unknown**
   - **Recommended next step**
   - **技术记录**
5. 在**What Guard observed**、确认最新的监控周期进度以及可用日志、扫描、播放器和源覆盖范围的报告名称。
6. 如果下一步表明不需要干预，请将报告保留为第一个成功结果。如果它指出缺少源或已停止的进程，请按照[故障排除](%E6%95%85%E9%9A%9C%E6%8E%92%E9%99%A4.md).

该报告可能会链接到技术证据以进行更深入的审查。普通操作员可以先阅读报告，仅在需要检查简单结果时才打开这些参考。

<a id="understand-quiet-reports"></a>
## 了解安静报告

玩家活动、案例审查和 Critical Guard 是事件驱动的。安静的服务器不应仅仅为了填补频道而产生虚构的玩家、案例或失败。可读结果可能表明来源已被检查，并且该报告中没有任何内容。

每日汇总有所不同：它使用当天会话、当前审核主题、保留的identity/case上下文、扫描进度以及 Guard 实际读取的来源差距为每个报告日期提供一次审核。可用服务器记录中缺少的事实仍然未知，而不是估计。

<a id="test-one-ordinary-player-session"></a>
## 测试一个普通玩家会话

当前第一个服务器状态报告后：

1. 让一名已知玩家正常加入和离开。
2. 等待下一个报告周期。
3. 打开玩家活动。
4. 确认它标识了 Guard 可用的帐户或显示名称、加入和离开时间、干净或不完整的会话结果、可用的先前历史记录以及下一步操作。

会话报告应包含观察到的数据。不应将其替换为文件名列表或存在记录的通用声明。
