<a id="ue4ss-loader-and-watchdog"></a>
## UE4SS ローダーとウォッチドッグ

`Scripts/main.lua`は、独立したウォッチドッグの起動、保存されたルートの検出、現在のログ末尾、サーバー エポックとセッション、制限されたポーリングとスキャン、object/worldコンテキスト、レビュー スコアリングを所有します。 `Admin.ini` 安全ゲート、従来の運用出力、およびレポート担当者への個別の引き継ぎ。遅い履歴作業が独立して再開される間、ライブポーリングを制限し続ける必要があります。ハートビート、起動マーカー、または増加`poll_id`は、そのコンポーネントのみを証明します。ルートを完了するには、同じ現在のブート、エポック、ポーリング、ソースの鮮度、レポート ペア、およびルート証明が必要です。

ソースとパッケージには 1 つの権限があります: `RandomDayGuard/Scripts/main.lua`。小文字の `scripts/` コピーは、ソース ツリーまたはリリースの一部ではありません。 1 つの標準的なスペルを維持すると、Windows または Linux でパッケージを抽出するときに大文字と小文字が衝突する障害が防止されます。

<a id="public-reporting-module"></a>
## パブリック レポート モジュール

`Scripts/public_pipeline.lua`は、ホスト認証情報やプロバイダー アダプターの代わりにコールバックを受け取ります。 8 つのソース クラスの一覧を作成し、終了状態と不完全な状態を記録し、現在のプレーヤーを保持された履歴から分離し、各ルートを `Observed`, `Interpretation`, `Unknown`, `Does not prove`, `Next action` と一致する必要があり、`Source references`、ルート証明を書き込みます。オプションの通知モードはローカル JSON 封筒のみ。配達を請求したり、配達を同梱したりすることはありません endpoint/bridge.

`tests/lua/public_pipeline_runtime_test.lua`の実行可能フィクスチャは、この出荷されたモジュールを Lua でロードし、完全なルートと期待される空のルートを証明し、欠落している現在のソース サイクルが閉じられなかったことを証明し、不完全なルートが送信ボックスに入らないことを証明します。

<a id="package-layout"></a>
## パッケージ レイアウト

ビルダーは、3 つのルート正当なファイル (`RandomDayGuard/` パスと空のランタイム プレースホルダー。メンバーをバイト単位で順序付けし、修正します。 ZIP メタデータ、正規ローダーを 1 回パッケージ化し、プライベート マテリアルのすべてのメンバーをスキャンし、SHA-256 をメンバーごとに使用し、名前とバイトを 1 つのコンテンツ ダイジェストにバインドし、2 回ビルドします。テストでは、大文字と小文字の衝突がすべて拒否され、通常の抽出ではアーカイブ エントリごとに物理ファイルが 1 つだけ生成されることが証明されています。

パブリック リポジトリには、現在のリリース フォルダーのみが保持されます。ビルダーはZIP、チェックサム、メモ、バージョン マーカー、ソース ツリーが一致します。

<a id="code-comment-contract"></a>
## コード コメント契約

実行時コメントは、簡潔な保守契約であり、2 番目のマニュアルではありません。出荷された各ランタイム モジュールは、最初のコメント ブロックに正規リンクを 1 つ配置する必要があります。

```lua
-- Documentation: docs/SOURCE_MODULE_REFERENCE.md#ue4ss-loader-and-watchdog
```

非明白な状態、スケジューリング、write/readback/rollback、ソース発見、翻訳、証拠、出力スキーマ、ルート ケイデンス、および編集ブロックは、該当する場合、次のラベルが付いた焦点を当てたコメントを使用します。

```lua
-- Public contract: <invariant or consequence>
-- Evidence boundary: <what the input cannot prove>
-- Failure behavior: <how the block fails closed or recovers>
-- Documentation: docs/<canonical-file>.md#<existing-anchor>
```

メイン ローダーには、設定用の焦点を当てた所有者コメントも 1 つあります。ロード、保存された検出、アトミック置換、強制、およびスケジュール。これらのコメントは、制御フローと障害の境界を示します。ランタイムの動作は変更されません。

バリデータは、ランタイム モジュールごとにモジュール レベルの `Documentation:` リンクを必要とし、すべてのコメント パスとアンカーを解決し、両方のランタイム モジュールで焦点を当てたコントラクトと失敗のコメントを必要とし、同じ正規リンクを `TRACEABILITY_INDEX.json` と比較します。コメントはトレーサビリティであり、実行時の証明ではありません。

<a id="contributor-change-checklist"></a>
## コントリビュータ変更チェックリスト

1. 1 つの所有モジュールとその対象となるフィクスチャを更新します。
2. 正規の構成、スキーマ、出力、証拠、またはライフサイクル セクションを更新します。
3. 実行 `python -B tools/generate_documentation_audit.py --write`設定、パッケージ化されたパス、生成された出力クラス、所有者、またはリカバリ コントラクトの変更後。
4. 実行 `python -B tools/generate_documentation_audit.py --check`、焦点を当てた単体テスト、Lua が利用可能な実際の Lua フィクスチャ、完全なバリデータ、2 つの独立した決定論的ビルド、および`git diff --check`.
5. 生成された内容を確認しますZIP リリースを作成する前にメンバー リスト、チェックサム、プライベート マテリアルをスキャンします。
