# Admin.ini 強制

> **正規の英語ソース:** [ADMIN_INI_ENFORCEMENT.md](../../ADMIN_INI_ENFORCEMENT.md). このローカライズされたドキュメントには、正確なコマンド、パス、キー、ステータス値、ハッシュ、ファイル名が保存されています。技術的な表現が異なる場合は、英語のソースを使用してください。


RandomDayGuard は、デフォルト設定のサーバー禁止リストを変更しません。管理者が確認するためのレポートのみが作成されます。このページでは、管理者が意図的に有効にしているオプションの禁止リストの自動更新について説明します。

<a id="what-guard-checks-before-changing-the-ban-list"></a>
## 禁止リストを変更する前に Guard がチェックする内容

Guard は、以下のすべての回答が **はい**:

1. 現在の証拠は、十分な信頼性を持って 1 つの特定のアカウントを特定しましたか?
2. そのアカウントはモデレーターでもありませんか?管理者が信頼できるとマークしたアカウントでもありませんか?
3. そのアカウントはまだ禁止リストに載っていませんか?
4. アカウントは設定された自動アクション スコアに達しましたか?
5. Guard は現在のスコアを読み取ることができますか?`Admin.ini`同じバックアップを保存しますか?
6. Guard がアップデートを準備している間、`Admin.ini`は変更されませんでしたか?
7. 保存後、完全なファイルは意図した結果と正確に一致しますか?

いずれかの回答が **いいえ** である場合、または確認できない場合、Guard は `Admin.ini`を変更しないままにします。そしてその理由を報告書に記録します。保存が開始されても最終チェックが失敗した場合、Guard は検証済みのバックアップを復元します。

<a id="file-format"></a>
## ファイル形式

`Admin.ini`はクリーンな禁止行のみを受け取る必要があります。

```ini
BannedPlayer=<ID>
```

- 名前なし。
- コメントなし。
- 理由なし。
- いいえ

<a id="safe-defaults"></a>
## 安全なデフォルト

```lua
review_only_mode = true
auto_ban = false
write_admin_ini = false
require_clean_ban_id = true
preserve_existing_bans = true
preserve_moderators = true
```

<a id="ban-id-source"></a>
## 禁止 ID ソース

最適なソース:

```text
Login request
Name=<player>
ConnectID=<raw_id>
UniqueId=<platform_id>
```

ランタイムは、完全な数値 ID または文書化された完全な`<digits>_+_|<non-space token>`接続フォームを受け入れ、そこから数値の禁止 ID を導出します。未知の接尾辞を持つ任意の数値接頭辞は拒否されます。

正解:

```ini
BannedPlayer=2535422284688820
```

誤:

```ini
BannedPlayer=ExamplePlayer
```

こちらも誤:

```text
BannedPlayer=<ID>
```

<a id="exact-settings-guard-checks"></a>
## 正確な設定 ガード チェック

これらの設定は、上記のチェックを実装します。リストされたすべての条件は true である必要があります。

```text
review_only_mode == false
auto_ban == true
write_admin_ini == true
ban_id is clean numeric
identity is mapped
not trusted
not moderator
threshold is met
account-specific evidence exists
```

いずれかの条件が false であるか、チェックできない場合、Guard は禁止リストを変更しないままにし、何が禁止されたのかを記録します。

<a id="transaction-safety"></a>
## トランザクションの安全性

唯一の`Admin.ini`変更パスは、次の手順を順番に実行します。

1. 権限のあるバイトを読み取り、構造的に検証します。
2. 同じスナップショットからモデレーター、信頼済み、および既存の禁止状態を導出します。
3. 一意のバックアップを`runtime/backups/` を実行し、バイト単位で検証します。
4. 置換直前に`Admin.ini`を再読み込みし、外部変更を拒否します。
5. 設定された制御された置換パスを通じて候補を書き込みます。
6. 完全なリードバック バイトが完全な候補バイトと等しくなるように要求します。
7. オンリードバックが失敗した場合は、現在のファイルが Guard によって書き込まれた正確な候補である間にのみ、検証済みのバックアップを復元します。別の作成者が変更した場合、Guard は未知の外部バイトを上書きするのではなく、ロールバックを拒否します。

重複 ID はべき等であり、2 行目や 2 番目のバックアップは書き込まれません。バックアップ名にはタイムスタンプ、ソースバイトのフィンガープリント、クリーン ID が含まれるため、別の試行では古い 1 秒ファイル名を共有できません。

<a id="local-regression-proof"></a>
## ローカル回帰証明

`tests/lua/enforcement_runtime_test.lua`は、出荷されたローダーを 1 回起動し、リポジトリ `append_ban()` クロージャを実行します。これには、挿入、重複冪等性、`.tmp/` ディレクトリの下にある分離された合成ファイルに対して実際のローカル moderator/trusted 拒否、脆弱で不正な ID の拒否、バイト正確なバックアップ検証、同時変更の拒否、リードバック失敗後の正常なロールバック、および書き込み後の外部変更の上書きの拒否が含まれます。そのファイルシステム ラッパーは、フィクスチャ ルート外のあらゆる突然変異を拒否します。実際のサーバー パスまたは実際の `Admin.ini` は使用されません。

それを実行してください。`python tools/test_public_pipeline.py`。フィクスチャ パスは、ローカル トランザクションの動作のみを証明します。強制の有効化、本番書き込みの承認、ホスト固有の権限の証明は行われません。

<a id="rollback"></a>
## ロールバック

1. サーバーを停止します。
2. 最新のAdmin.iniバックアップを`runtime/backups/`.
3. 必要に応じて、間違った`BannedPlayer=<ID>`行を削除します。
4. サーバーを起動します。
5. 再度開きAdmin.ini、行が存続するか削除されたことを確認します。
6. 保存`enforced_bans.jsonl`
