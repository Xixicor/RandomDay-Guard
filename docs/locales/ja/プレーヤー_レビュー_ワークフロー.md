# プレーヤーのレビュー ワークフロー

> **正規の英語ソース:** [PLAYER_REVIEW_WORKFLOW.md](../../PLAYER_REVIEW_WORKFLOW.md). このローカライズされたドキュメントには、正確なコマンド、パス、キー、ステータス値、ハッシュ、ファイル名が保存されています。技術的な表現が異なる場合は、英語のソースを使用してください。


このページは、1 人のプレーヤー、アカウント、またはケースに対して使用してください。目的は、自動化された告発ではなく、再現可能なレビュー決定です。

<a id="quick-path"></a>
## クイック パス

1. 開く `runtime/final_logs/player_activity_latest.json`.
2. ルート ステータスを確認します`runtime/final_logs/route_proof.json`.
3. どの観察が現在でどの観察が過去のものであるかを特定します。
4. 引用されたアイデンティティとセッション ソース参照を確認します。
5. 推論前のレビュー`case_review_latest.json`相関するケースが存在する場合。
6. アクションを選択する前に、不明な点を記録し、`does_not_prove`アクションを選択します。
7. 個別の施行が行われない限り、施行は無効のままにしておきます。ゲートは実証済みです。

<a id="1-confirm-route-proof"></a>
## 1.ルート証明の確認

プレーヤーのルートを次のように解釈します。

| ステータス | アクション |
|---|---|
| `full` | ソース制限を確認しながら続行します。 |
| `limited_expected_empty` | 実際に存在する主題のみを使用して続行します。行方不明のプレーヤーやケースをでっち上げないでください。 |
| `missing` | プレーヤーの決定を停止し、ルートのトラブルシューティングを行います。 |

健全なスケジューラーはルート証明に代わるものではありません。

<a id="2-establish-identity"></a>
## 2. ID を確立する

サーバーに公開された ID 証拠によって裏付けられたクリーンなアカウント ID を推奨します。また、利用可能な場合は、PlayerData ファイル名。生のソース参照を保持します。

次のようなものは強制しないでください。

- 表示名のみ、
- 通知またはホスティング パネルに表示される名前、
- タイミングの類似性、
- マッピングされていない ID または信頼性の低い ID。
- 現時点での裏付けのない過去のレポート。

<a id="3-separate-current-from-historical"></a>
## 3.現在と過去を区別する

現在の証拠は、アクティブなレポート ウィンドウまたはサーバー エポックを説明します。歴史的証拠はパターンを説明する可能性がありますが、現在のウィンドウのギャップを黙って埋めることはできません。

両方のスコープを個別に記録します。

```text
Current observations:
Current source references:
Historical context:
Historical source references:
```

<a id="4-review-observations-and-interpretation"></a>
## 4.観察と解釈を確認する

報告書のこれらのセクションを明確に読んでください。

```text
observed
interpretation
unknown
does_not_prove
next_action
source_references
```

重要な決定について引用された構造化された証拠を再度開きます。翻訳はナビゲーションと説明であり、新しい証拠ではありません。

<a id="5-calibrate-the-decision"></a>
## 5.決定を調整します。

| 決定 | 次の場合に使用します。 |
|---|---|
| `INFO` | 通常または低コンテキストの観察。 |
| `WATCH` | 監視する価値のある弱い信号または不完全な信号。 |
| `REVIEW` | 相関する証拠には管理者の判断が必要。 |
| `BAN-ELIGIBLE` | クリーンな ID と設定された証拠のしきい値満たされています。書き込みゲートは引き続き適用されます。 |
| `AUTO-BANNED` | 強制は明示的に有効化され、バックアップ、書き込み、リードバック、監査はすべて成功しました。 |

有罪または意図を証明する決定ラベルはありません。

<a id="6-apply-the-evidence-boundary"></a>
## 6.証拠の境界を適用する

クラッシュ、再接続、警告、object/classトークン、およびケースのグループ化により、レビューをサポートできます。それらだけでは、不正行為、盗難、複製、所有権、直接的な損害、または事件の因果関係を証明することはできません。

ID、解析、バックアップ、書き込み、リードバック、またはロールバックが弱い場合、または失敗した場合は、適用は失敗して終了する必要があります。
