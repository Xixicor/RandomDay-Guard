# ここから始めてください: 最初の Guard レポートをお読みください

> **正規の英語ソース:** [START_HERE.md](../../START_HERE.md). このローカライズされたドキュメントには、正確なコマンド、パス、キー、ステータス値、ハッシュ、ファイル名が保存されています。技術的な表現が異なる場合は、英語のソースを使用してください。


このガイドはRandomDayGuard がインストールされ、有効になっています。これは、新しいオペレーターにソース コード、パッケージ内部、マシンのみのステータス ファイルの検査を依頼することなく、有益な結果の 1 つを証明します。

<a id="what-happens-after-the-server-starts"></a>
## サーバーの起動後に起こること

ガードはゲームサーバーを待機し、UE4SS をロードし、サーバーの使用可能なレコードを見つけて、限定されたバックグラウンド スキャンを開始します。古い履歴がまだインデックス付けされている間に、現在のサーバーの健全性をレポートできます。

最初のレポートは **サーバー ステータス** である必要があります。 Guard が監視サイクルを現在完了しているかどうか、タイムスタンプが利用可能な場合は現在のサーバーの実行がいつ開始されたか、active/rotatedログとスキャンのカバレッジがどのくらい存在するか、接続されているプレーヤーの数、どのソース グループが欠落しているか、オペレータのアクションが必要かどうかが答えられます。

進行中のバックグラウンド スキャンは履歴カバレッジの制限であり、自動的に起動エラーになるわけではありません。 Guard は、スキャン カーソル、完了したファイル、検出されたファイル、および最終進行時間を記録します。監視サイクルを繰り返してもこれらの値が変化しなくなった場合は、履歴パスが停止しているものとして扱い、トラブルシューティングのスキャン分岐に従います。古い履歴が不完全であるという理由だけで、現在のログとセッションの結果を破棄しないでください。

<a id="read-the-first-server-status-report"></a>
## 最初のサーバー ステータス レポートを読みます。

1. 専用サーバーを通常どおり起動します。
2. ゲームサーバーを待ってUE4SS で開始を完了します。
3. 開く RandomDayGuard's 最終レポート フォルダーを選択し、読み取り可能な最新のサーバー ステータス レポートを選択します。
4. レポートに次の内容が含まれていることを確認します。
   - **概要**
   - **Guard が観察した内容**
   - **意味**
   - **不明な点**
   - **推奨される次のステップ**
   - **技術記録**
5. **Guard が観察した内容**の量が回答され、最新の監視サイクルが進んでいることと、レポート名が利用可能なログ、スキャン、プレーヤー、およびソース カバレッジであることを確認します。
6. 次のステップで介入が必要ないと判断された場合は、レポートを最初の成功した結果として保持します。欠落しているソースまたは停止したプロセスの名前が記載されている場合は、[トラブルシューティング](%E3%83%88%E3%83%A9%E3%83%96%E3%83%AB%E3%82%B7%E3%83%A5%E3%83%BC%E3%83%86%E3%82%A3%E3%83%B3%E3%82%B0.md).

レポートは、より詳細なレビューのための技術的証拠にリンクされている場合があります。通常のオペレーターは、最初にレポートを読み、単純な結果を確認する必要がある場合にのみそれらの参照を開くことができます。

<a id="understand-quiet-reports"></a>
## 静かなレポートを理解する

プレーヤーのアクティビティ、ケースレビュー、およびクリティカル ガードはイベント駆動型です。静かなサーバーは、単にチャンネルを埋めるために架空のプレーヤー、事件、または失敗を生成するべきではありません。読み取り可能な結果には、ソースがチェックされ、そのレポートには何も含まれていなかったことが示される場合があります。

日次ロールアップは異なります。同日のセッション、現在のレビュー対象、保持されているidentity/caseコンテキスト、スキャンの進行状況、Guard が実際に読み取ることができるソース ギャップを使用して、レポート日付ごとに 1 つのレビューが提供されます。利用可能なサーバー レコードにない事実は、推定されるのではなく不明のままです。

<a id="test-one-ordinary-player-session"></a>
## 通常のプレーヤー セッションを 1 つテストします。

最初のサーバー ステータス レポートが最新になったら:

1. 既知のプレーヤー 1 人が通常通りに参加し、離脱できるようにします。
2. 次のレポート サイクルを待ちます。
3. プレーヤーを開く
4. Guard で使用できるアカウントまたは表示名、参加時間と退席時間、クリーンまたは不完全なセッション結果、以前の履歴（利用可能な場合）、および次の 1 つのアクションが識別されていることを確認します。

セッション レポートには、観察されたデータが含まれている必要があります。ファイル名のリストや、レコードが存在するという一般的なステートメントに置き換えるべきではありません。
