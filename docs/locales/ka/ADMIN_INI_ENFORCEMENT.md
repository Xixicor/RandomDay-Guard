# Admin.ini აღსრულება

> **კანონიკური ინგლისური წყარო:** [ADMIN_INI_ENFORCEMENT.md](../../ADMIN_INI_ENFORCEMENT.md). ეს ლოკალიზებული დოკუმენტაცია ინახავს ზუსტ ბრძანებებს, ბილიკებს, გასაღებებს, სტატუსის მნიშვნელობებს, ჰეშებსა და ფაილების სახელებს. თუ ტექნიკური ფორმულირება განსხვავდება, გამოიყენეთ ინგლისური წყარო.


RandomDayGuard არ ცვლის სერვერის აკრძალვის სიას ნაგულისხმევ დაყენებაში. ის ქმნის მხოლოდ ანგარიშებს ადმინისტრატორის განსახილველად. ეს გვერდი განმარტავს არასავალდებულო ავტომატური აკრძალვის სიის განახლებას ადმინისტრატორებისთვის, რომლებიც შეგნებულად ჩართავს მას.

<a id="what-guard-checks-before-changing-the-ban-list"></a>
## რას ამოწმებს მცველი აკრძალვის სიის შეცვლამდე

Guard ამატებს აკრძალვას მხოლოდ მაშინ, როდესაც ქვემოთ მოცემული ყველა პასუხი არის **დიახ**:

1. ამჟამინდელმა მტკიცებულებებმა დაადგინეს ერთი კონკრეტული ანგარიში საკმარისი სანდოობით?
2. არ არის ანგარიში არც მოდერატორი და არც ანგარიში ადმინისტრატორის მიერ მონიშნულია სანდო?
3. ანგარიში უკვე არ არის აკრძალვის სიაში?
4. მიაღწია თუ არა ანგარიშმა კონფიგურირებულ ავტომატური მოქმედების ქულას?
5. შეუძლია მცველს წაიკითხოს მიმდინარე `Admin.ini` და შეინახოთ იდენტური სარეზერვო ასლი?
6. გააკეთა `Admin.ini` დარჩეს უცვლელი, სანამ დაცვა ამზადებდა განახლებას?
7. შენახვის შემდეგ, სრული ფაილი ზუსტად ემთხვევა დანიშნულ შედეგს?

თუ რაიმე პასუხია **არა**, ან მისი შემოწმება შეუძლებელია, მცველი ტოვებს `Admin.ini` უცვლელია და აფიქსირებს მიზეზს თავის ანგარიშებში. თუ შენახვა დაიწყება, მაგრამ საბოლოო შემოწმება ვერ მოხერხდა, Guard აღადგენს დამოწმებულ სარეზერვო ასლს.

<a id="file-format"></a>
## ფაილის ფორმატი

`Admin.ini` უნდა მიიღოს მხოლოდ სუფთა აკრძალვის ხაზები:

```ini
BannedPlayer=<ID>
```

- სახელები არ არის.
- კომენტარები არ არის.
- მიზეზები არ არის.
- სუფიქსები არ არის.

<a id="safe-defaults"></a>
## უსაფრთხო ნაგულისხმევი პარამეტრები

```lua
review_only_mode = true
auto_ban = false
write_admin_ini = false
require_clean_ban_id = true
preserve_existing_bans = true
preserve_moderators = true
```

<a id="ban-id-source"></a>
## აკრძალვის ID წყარო

საუკეთესო წყარო:

```text
Login request
Name=<player>
ConnectID=<raw_id>
UniqueId=<platform_id>
```

გაშვების დრო იღებს ან სრულად ციფრულ ID-ს ან სრულ დოკუმენტურ `<digits>_+_|<non-space token>` კავშირის ფორმა და მისგან გამოაქვს ციფრული აკრძალვის ID. თვითნებური რიცხვითი პრეფიქსები უცნობი სუფიქსით უარყოფილია; ისინი არ არის შეკვეცილი აკრძალვის ID-ში.

სწორია:

```ini
BannedPlayer=2535422284688820
```

არასწორია:

```ini
BannedPlayer=ExamplePlayer
```

ასევე არასწორია:

```text
BannedPlayer=<ID>
```

<a id="exact-settings-guard-checks"></a>
## ზუსტი პარამეტრების დაცვა ამოწმებს

ეს პარამეტრები ახორციელებს ზემოთ აღწერილ შემოწმებებს. ყველა ჩამოთვლილი პირობა უნდა იყოს ჭეშმარიტი:

```text
review_only_mode == false
auto_ban == true
write_admin_ini == true
ban_id is clean numeric
identity is mapped
not trusted
not moderator
threshold is met
account-specific evidence exists
```

თუ რომელიმე პირობა მცდარია ან მისი შემოწმება შეუძლებელია, მცველი ტოვებს აკრძალვის სიას უცვლელად და ჩაწერს, რამ შეაჩერა იგი.

<a id="transaction-safety"></a>
## ტრანზაქციის უსაფრთხოება

ერთადერთი `Admin.ini` მუტაციის გზა ასრულებს შემდეგ ნაბიჯებს თანმიმდევრობით:

1. წაიკითხეთ და სტრუქტურულად დაადასტურეთ ავტორიტეტული ბაიტები.
2. გამოიყვანეთ მოდერატორი, სანდო და არსებული აკრძალვის მდგომარეობა იმავე სნეპშოტიდან.
3. ჩაწერეთ უნიკალური სარეზერვო ასლი ქვეშ `runtime/backups/` და გადაამოწმეთ ის ბაიტი ბაიტისთვის.
4. ხელახალი წაკითხვა `Admin.ini` ჩანაცვლებამდე დაუყოვნებლივ და უარყოთ ნებისმიერი გარე ცვლილება.
5. ჩაწერეთ კანდიდატი კონფიგურირებული, კონტროლირებადი ჩანაცვლების გზაზე.
6. მოითხოვეთ სრული წაკითხვის ბაიტები, რათა ტოლი იყოს სრული კანდიდატი ბაიტები.
7. წაკითხვის წარუმატებლობის შემთხვევაში, აღადგინეთ დამოწმებული სარეზერვო ასლი მხოლოდ მაშინ, როდესაც მიმდინარე ფაილი ჯერ კიდევ არის Guard-ის მიერ დაწერილი ზუსტი კანდიდატი. თუ სხვა დამწერმა შეცვალა ის, Guard უარს იტყვის უკან დაბრუნებაზე, ვიდრე უცნობი გარე ბაიტების გადაწერა.

დუბლიკატი ID-ები არაეფექტურია: არც მეორე ხაზი და არც მეორე სარეზერვო ასლი არ იწერება. სარეზერვო სახელები მოიცავს დროის ანაბეჭდს, წყაროს ბაიტის ანაბეჭდს და სუფთა ID-ს, ამიტომ ცალკეული მცდელობები ვერ გაზიარებს ძველი ერთი წამის ფაილის სახელს.

<a id="local-regression-proof"></a>
## ლოკალური რეგრესიის მტკიცებულება

`tests/lua/enforcement_runtime_test.lua` ჩატვირთავს გაგზავნილ ჩამტვირთველს ერთხელ და შემდეგ ახორციელებს მის რეალურ ლოკალურს `append_ban()` დახურვა საცავის ქვემოთ იზოლირებული სინთეტიკური ფაილებისგან `.tmp/` დირექტორია. იგი მოიცავს ჩასმას, დუბლიკატულ იდემპოტენციას, moderator/trusted უარყოფა, სუსტი და არასწორი იდენტობის უარყოფა, ბაიტის ზუსტი სარეზერვო დადასტურება, ერთდროული მოდიფიკაციის უარყოფა, წარმატებული დაბრუნება წარუმატებელი წაკითხვის შემდეგ და უარი ჩაწერის შემდგომი გარე ცვლილების გადაწერაზე. მისი ფაილური სისტემის შეფუთვა უარყოფს ნებისმიერ მუტაციას სამაგრის ფესვის გარეთ; არ არის რეალური სერვერის გზა ან რეალური `Admin.ini` გამოიყენება.

გაუშვით `python tools/test_public_pipeline.py`. ფიქსაციის საშვი ადასტურებს მხოლოდ ლოკალური ტრანზაქციის ქცევას. ის არ ააქტიურებს აღსრულებას, არ აძლევს პროდუქციის ჩაწერის ავტორიზაციას ან არ ადასტურებს ჰოსტის სპეციფიკურ ნებართვებს.

<a id="rollback"></a>
## უკან

1. გააჩერეთ სერვერი.
2. აღადგინეთ უახლესი Admin.ini სარეზერვო ასლი `runtime/backups/`.
3. წაშალეთ არასწორი `BannedPlayer=<ID>` ხაზი.
4. გაუშვით სერვერი.
5. ხელახლა გახსნა Admin.ini და დაადასტურეთ, რომ ხაზი შენარჩუნებულია ან წაიშალა.
6. შენახვა `enforced_bans.jsonl` აუდიტისთვის.
