# დაიწყეთ აქ: წაიკითხეთ გვარდიის პირველი ანგარიში

> **კანონიკური ინგლისური წყარო:** [START_HERE.md](../../START_HERE.md). ეს ლოკალიზებული დოკუმენტაცია ინახავს ზუსტ ბრძანებებს, ბილიკებს, გასაღებებს, სტატუსის მნიშვნელობებს, ჰეშებსა და ფაილების სახელებს. თუ ტექნიკური ფორმულირება განსხვავდება, გამოიყენეთ ინგლისური წყარო.


ეს სახელმძღვანელო იწყება RandomDayGuard დაინსტალირებული და ჩართულია. ის ადასტურებს ერთ სასარგებლო შედეგს ახალი ოპერატორისთვის წყაროს კოდის, პაკეტის შიდა ნაწილების ან მხოლოდ მანქანის სტატუსის ფაილების შემოწმების თხოვნის გარეშე.

<a id="what-happens-after-the-server-starts"></a>
## რა ხდება სერვერის გაშვების შემდეგ

მცველი ელოდება თამაშის სერვერს და UE4SS ჩასატვირთად, პოულობს სერვერის ხელმისაწვდომ ჩანაწერებს და იწყებს შემოსაზღვრული ფონის სკანირებას. მას შეუძლია შეატყობინოს მიმდინარე სერვერის ჯანმრთელობას, სანამ ძველი ისტორია ჯერ კიდევ ინდექსირებულია.

პირველი ანგარიში უნდა იყოს **სერვერის სტატუსი**. ის პასუხობს, ასრულებს თუ არა გვარდია მონიტორინგის ციკლებს ახლა, როდესაც მიმდინარე სერვერის გაშვება დაიწყო, თუ ეს დროის ანაბეჭდი ხელმისაწვდომია, რამდენი active/rotated არსებობს ჟურნალის და სკანირების დაფარვა, რამდენი მოთამაშეა დაკავშირებული, რომელი წყაროს ჯგუფები აკლია და საჭიროა თუ არა ოპერატორის მოქმედება.

ფონის სკანირება, რომელიც ჯერ კიდევ მიმდინარეობს, არის ისტორიული გაშუქების შეზღუდვა და არა ავტომატურად გაშვების მარცხი. მცველი იწერს სკანირების კურსორს, დასრულებულ ფაილებს, აღმოჩენილ ფაილებს და ბოლო პროგრესის დროს. თუ ეს მნიშვნელობები შეწყვეტს ცვლილებას მონიტორინგის განმეორებით ციკლებში, მიიჩნიეთ ისტორიული გზა შეჩერებულად და მიჰყევით სკანირების ფილიალს პრობლემების მოგვარებაში. არ გადააგდოთ მიმდინარე ჟურნალი და სესიის შედეგები მხოლოდ იმიტომ, რომ ძველი ისტორია არასრულია.

<a id="read-the-first-server-status-report"></a>
## წაიკითხეთ სერვერის სტატუსის პირველი ანგარიში

1. ჩართეთ გამოყოფილი სერვერი ნორმალურად.
2. დაელოდეთ თამაშის სერვერს და UE4SS დასასრულებლად.
3. გახსენით RandomDayGuard's საბოლოო ანგარიშების საქაღალდე და აირჩიეთ უახლესი იკითხებადი სერვერის სტატუსის ანგარიში.
4. დაადასტურეთ, რომ ანგარიში შეიცავს:
   - **შეჯამება**
   - **რა დააკვირდა მცველმა**
   - **რას ნიშნავს**
   - **რა რჩება უცნობი**
   - **რეკომენდირებულია შემდეგი ნაბიჯი**
   - **ტექნიკური ჩანაწერი**
5. ში **რა დააკვირდა მცველმა**, დაადასტურეთ მონიტორინგის ციკლის უახლესი მიღწევები და ანგარიშის სახელები ხელმისაწვდომი ჟურნალის, სკანირების, დამკვრლის და წყაროს გაშუქების შესახებ.
6. თუ შემდეგი ნაბიჯი ამბობს, რომ ჩარევა არ არის საჭირო, შეინახეთ ანგარიში, როგორც პირველი წარმატებული შედეგი. თუ ის ასახელებს გამოტოვებულ წყაროს ან შეჩერებულ პროცესს, მიჰყევით ზუსტად ამ სიმპტომს [პრობლემების აღმოფხვრა](%E1%B2%9E%E1%B2%A0%E1%B2%9D%E1%B2%91%E1%B2%9A%E1%B2%94%E1%B2%9B%E1%B2%94%E1%B2%91%E1%B2%98%E1%B2%A1_%E1%B2%90%E1%B2%A6%E1%B2%9B%E1%B2%9D%E1%B2%A4%E1%B2%AE%E1%B2%95%E1%B2%A0%E1%B2%90.md).

ანგარიში შეიძლება დაუკავშირდეს ტექნიკურ მტკიცებულებებს უფრო ღრმა განხილვისთვის. ჩვეულებრივ ოპერატორს შეუძლია ჯერ წაიკითხოს მოხსენება და გახსნას ეს მითითებები მხოლოდ მაშინ, როდესაც საჭიროა მარტივი შედეგის შემოწმება.

<a id="understand-quiet-reports"></a>
## მშვიდი ანგარიშების გაგება

მოთამაშის აქტივობა, შემთხვევის განხილვა და კრიტიკული მცველი მოვლენებზეა ორიენტირებული. მშვიდი სერვერი არ უნდა აწარმოებდეს გამოგონილ მოთამაშეს, ქეისს ან უბრალოდ არხის შევსებას. წაკითხვადი შედეგი შეიძლება ითქვას, რომ წყარო შემოწმდა და არაფერი ეკუთვნოდა ამ ანგარიშს.

დღიური შეკრება განსხვავებულია: ის უზრუნველყოფს ერთ მიმოხილვას თითო ანგარიშის თარიღზე იმავე დღის სესიების, მიმდინარე განხილვის საგნების, შენახული identity/case კონტექსტი, სკანირება პროგრესი და წყაროს ხარვეზები, რომელთა წაკითხვაც მცველს შეუძლია. ფაქტები, რომლებიც არ არის ხელმისაწვდომი სერვერის ჩანაწერებში, შეფასების ნაცვლად უცნობი რჩება.

<a id="test-one-ordinary-player-session"></a>
## გამოსცადეთ ერთი ჩვეულებრივი მოთამაშის სესია

როგორც პირველი სერვერის სტატუსის ანგარიში იქნება აქტუალური:

1. ნება მიეცით ერთ ცნობილ მოთამაშეს შეუერთდეს და დატოვოს ჩვეულებრივად.
2. დაელოდეთ მოხსენების შემდეგ ციკლს.
3. გახსენით მოთამაშის აქტივობა.
4. დაადასტურეთ, რომ ის განსაზღვრავს ანგარიშს ან საჩვენებელ სახელს, რომელიც ხელმისაწვდომია Guard-ისთვის, შეერთების და გასვლის დრო, სუფთა ან არასრული სესიის შედეგი, წინა ისტორია, როდესაც ხელმისაწვდომია, და ერთი შემდეგი მოქმედება.

სესიის ანგარიში უნდა შეიცავდეს დაკვირვებულ მონაცემებს. ის არ უნდა შეიცვალოს ფაილის სახელების სიით ან ჩანაწერების არსებობის ზოგადი განცხადებით.
