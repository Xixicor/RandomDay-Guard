# მოთამაშის მიმოხილვის სამუშაო პროცესი

> **კანონიკური ინგლისური წყარო:** [PLAYER_REVIEW_WORKFLOW.md](../../PLAYER_REVIEW_WORKFLOW.md). ეს ლოკალიზებული დოკუმენტაცია ინახავს ზუსტ ბრძანებებს, ბილიკებს, გასაღებებს, სტატუსის მნიშვნელობებს, ჰეშებსა და ფაილების სახელებს. თუ ტექნიკური ფორმულირება განსხვავდება, გამოიყენეთ ინგლისური წყარო.


გამოიყენეთ ეს გვერდი ერთი მოთამაშისთვის, ანგარიშისთვის ან ქეისისთვის. მიზანია განმეორებადი განხილვის გადაწყვეტილება და არა ავტომატური ბრალდება.

<a id="quick-path"></a>
## სწრაფი გზა

1. გახსენით `runtime/final_logs/player_activity_latest.json`.
2. დაადასტურეთ მარშრუტის სტატუსი `runtime/final_logs/route_proof.json`.
3. დაადგინეთ რომელი დაკვირვებებია აქტუალური და რომელი ისტორიული.
4. შეამოწმეთ მითითებული პირადობის და სესიის წყაროს მითითებები.
5. გადახედვა `case_review_latest.json` როდესაც არსებობს დაკავშირებული შემთხვევა.
6. ჩაწერეთ უცნობი და `does_not_prove` მოქმედების არჩევამდე.
7. დატოვეთ აღსრულების გათიშვა, თუ არ არის დადასტურებული ცალკეული აღსრულების კარიბჭეები.

<a id="1-confirm-route-proof"></a>
## 1. დაადასტურეთ მარშრუტის დადასტურება

მოთამაშის მარშრუტის ინტერპრეტაცია როგორც:

| სტატუსები | მოქმედება |
|---|---|
| `full` | გააგრძელეთ წყაროს ლიმიტების გადახედვისას. |
| `limited_expected_empty` | განაგრძეთ მხოლოდ რეალურად არსებული სუბიექტებით; არ გამოიგონოთ დაკარგული მოთამაშე ან საქმე. |
| `missing` | შეაჩერეთ მოთამაშის გადაწყვეტილება და მოაგვარეთ მარშრუტი. |

ჯანსაღი განრიგები არ ცვლის მარშრუტის მტკიცებულებას.

<a id="2-establish-identity"></a>
## 2. დაადგინეთ ვინაობა

აჯობეთ სუფთა ანგარიშის იდენტიფიკატორი, რომელიც დადასტურებულია სერვერის მიერ გამოვლენილი პირადობის მტკიცებულებებით და, სადაც ეს შესაძლებელია, PlayerData ფაილის სახელები. შეინახეთ დაუმუშავებელი წყაროს მითითება.

არ განახორციელოთ:

- მხოლოდ საჩვენებელი სახელი;
- შეტყობინებების ან ჰოსტინგის პანელში ნაჩვენები სახელი;
- დროის მსგავსება;
- გაურკვეველი ან სუსტი სანდო იდენტობა;
- ისტორიული ანგარიში მიმდინარე დადასტურების გარეშე.

<a id="3-separate-current-from-historical"></a>
## 3. გამოყავით მიმდინარე ისტორიულიდან

მიმდინარე მტკიცებულება აღწერს აქტიური მოხსენების ფანჯარას ან სერვერის ეპოქას. ისტორიულმა მტკიცებულებებმა შეიძლება ახსნას ნიმუში, მაგრამ მას არ შეუძლია ჩუმად შეავსოს ხარვეზები მიმდინარე ფანჯარაში.

ჩაწერეთ ორივე დიაპაზონი დამოუკიდებლად:

```text
Current observations:
Current source references:
Historical context:
Historical source references:
```

<a id="4-review-observations-and-interpretation"></a>
## 4. გადახედეთ დაკვირვებებსა და ინტერპრეტაციებს

მკაფიოდ წაიკითხეთ ანგარიშის სექციები:

```text
observed
interpretation
unknown
does_not_prove
next_action
source_references
```

ხელახლა გახსენით ციტირებული სტრუქტურირებული მტკიცებულება ნებისმიერი მატერიალური გადაწყვეტილების მისაღებად. თარგმანი არის ნავიგაცია და ახსნა და არა ახალი მტკიცებულება.

<a id="5-calibrate-the-decision"></a>
## 5. გადაწყვეტილების დაკალიბრება

| გადაწყვეტილება | გამოიყენეთ როცა |
|---|---|
| `INFO` | ნორმალური ან დაბალი კონტექსტის დაკვირვება. |
| `WATCH` | სუსტი ან არასრული სიგნალი ღირს მონიტორინგი. |
| `REVIEW` | დაკავშირებულ მტკიცებულებებს სჭირდება ადმინისტრატორის გადაწყვეტილება. |
| `BAN-ELIGIBLE` | სუფთა პირადობის და კონფიგურირებული მტკიცებულების ზღურბლები დაკმაყოფილებულია; ჩაწერის კარიბჭე კვლავ მოქმედებს. |
| `AUTO-BANNED` | აღსრულება ცალსახად ჩართული იყო და სარეზერვო ასლის შექმნა, ჩაწერა, წაკითხვა და აუდიტი წარმატებით დასრულდა. |

არც ერთი გადაწყვეტილების ეტიკეტი არ ადასტურებს დანაშაულს ან განზრახვას.

<a id="6-apply-the-evidence-boundary"></a>
## 6. გამოიყენეთ მტკიცებულების საზღვრები

ავარია, ხელახლა დაკავშირება, გაფრთხილებები, object/class ჟეტონები და შემთხვევების დაჯგუფებამ შეიძლება მხარი დაუჭიროს განხილვას. მარტო ისინი არ ადასტურებენ მოტყუებას, ქურდობას, დუბლირებას, საკუთრებას, პირდაპირ ზიანს ან ინციდენტის გამომწვევ მიზეზებს.

თუ იდენტიფიკაცია, ანალიზი, სარეზერვო ასლი, ჩაწერა, წაკითხვა ან უკან დაბრუნება სუსტია ან წარუმატებელია, აღსრულება უნდა ვერ დაიხუროს.
