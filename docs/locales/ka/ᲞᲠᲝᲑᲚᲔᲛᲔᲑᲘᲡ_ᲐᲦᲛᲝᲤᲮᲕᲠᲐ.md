# პრობლემების აღმოფხვრა

> **კანონიკური ინგლისური წყარო:** [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md). ეს ლოკალიზებული დოკუმენტაცია ინახავს ზუსტ ბრძანებებს, ბილიკებს, გასაღებებს, სტატუსის მნიშვნელობებს, ჰეშებსა და ფაილების სახელებს. თუ ტექნიკური ფორმულირება განსხვავდება, გამოიყენეთ ინგლისური წყარო.


გამოიყენეთ ეს გვერდი, როდესაც Guard არ იტვირთება, წყაროს შეგროვება შეუძლებელია, ანგარიში არ გამოჩნდება, ან მარშრუტის მტკიცებულება ეწინააღმდეგება იმას, რასაც ელოდით. დაიწყეთ გადაწყვეტილების ხით და მიჰყევით ერთ ტოტს. გამოიყენეთ გამოყოფილი [სტატუსის და შეცდომის მითითება](%E1%B2%A1%E1%B2%A2%E1%B2%90%E1%B2%A2%E1%B2%A3%E1%B2%A1%E1%B2%98%E1%B2%A1_%E1%B2%93%E1%B2%90_%E1%B2%A8%E1%B2%94%E1%B2%AA%E1%B2%93%E1%B2%9D%E1%B2%9B%E1%B2%98%E1%B2%A1_%E1%B2%9B%E1%B2%98%E1%B2%97%E1%B2%98%E1%B2%97%E1%B2%94%E1%B2%91%E1%B2%90.md) მხოლოდ მას შემდეგ, რაც წარუმატებელი ფენა ცნობილია.

კონფიგურაციის შეცვლამდე ან ხელახლა ინსტალაციამდე შეინახეთ მიმდინარე გაშვების ფაილები. შემორჩენილი ან დაკარგული არტეფაქტი განსაზღვრავს წარუმატებელ ეტაპს; განმეორებით გადატვირთვამ შეიძლება წაშალოს ეს მტკიცებულება.

<a id="choose-the-failure-path"></a>
## აირჩიეთ წარუმატებლობის გზა

<a id="1-decide-whether-guard-loaded"></a>
### 1. გადაწყვიტეთ დატვირთულია თუ არა მცველი

- **არა `runtime/` ფაილები არსებობს:** მიჰყევით [აღადგინეთ დაკარგული დროის ფაილები](#restore-missing-runtime-files). დაადასტურეთ ინსტალაციის გზა, კანონიკური ჩამტვირთავი, `enabled.txt` და `mods.txt` ანგარიშების გამოძიებამდე.
- **ამჟამინდელი სტატუსის ფაილები არსებობს:** მცველი ჩატვირთულია საკმარისად შორს, რომ ჩაწეროს მდგომარეობა. გააგრძელეთ ნაბიჯი 2; ხელახლა ინსტალაცია არ არის პირველი პასუხი.

<a id="2-decide-whether-the-scheduler-is-advancing"></a>
### 2. გადაწყვიტეთ მიიწევს თუ არა განრიგი

გახსნა:

```text
runtime/current/startup_status.json
runtime/current/poll_status.json
```

- **მრიცხველები და დროის ანაბეჭდები წინსვლა:** გააგრძელეთ ნაბიჯი 3.
- **`poll_id` სტატიკურია, `poll_in_flight` რჩება ჭეშმარიტი, ან გრაფიკის სტატუსი არ მუშაობს:** მიჰყევით [ჩარჩენილი გამოკითხვის ციკლის აღდგენა](#recover-a-stuck-poll-loop).
- **საბაზისო სკანირება მოლოდინშია, სანამ განრიგის პროგრესი გრძელდება:** ეს გაფრთხილებაა და არა ავტომატურად წარუმატებელი გაშვება. გამოიკვლიეთ მხოლოდ იმ შემთხვევაში, თუ ჩამორჩენა ან სკანირების პროგრესი შეჩერდება.

<a id="3-classify-route-proof"></a>
### 3. მარშრუტის მტკიცებულების კლასიფიკაცია

გახსენით `runtime/final_logs/route_proof.json` და შეამოწმეთ ყველა მარშრუტი ცალკე.

- **`full`:** შეადარეთ მოულოდნელი ფორმულირება მიმდინარე `source_references` და გვარი. არ შეცვალოთ მიწოდება, რადგან მხოლოდ ფორმულირება არასწორია.
- **`limited_expected_empty`:** დაადასტურეთ, რომ წყაროს აღრიცხვა მხარს უჭერს ლეგიტიმურ ცარიელ შედეგს. არ შექმნათ სინთეტიკური პლეერი ან ქეისი.
- **`missing`:** მიჰყევით [გამოტოვებული მარშრუტის დიაგნოსტიკა](#diagnose-a-missing-route).

<a id="4-classify-source-coverage"></a>
### 4. წყაროს გაშუქების კლასიფიკაცია

- **`partial`, `deferred`, `unavailable`, `malformed`, `permission_denied` ან `error`:** მიჰყევით [არასრული წყაროს დაფარვის ინტერპრეტაცია](#interpret-incomplete-source-coverage), შემდეგ მოძებნეთ ზუსტი კოდი [სტატუსისა და შეცდომის მითითება](%E1%B2%A1%E1%B2%A2%E1%B2%90%E1%B2%A2%E1%B2%A3%E1%B2%A1%E1%B2%98%E1%B2%A1_%E1%B2%93%E1%B2%90_%E1%B2%A8%E1%B2%94%E1%B2%AA%E1%B2%93%E1%B2%9D%E1%B2%9B%E1%B2%98%E1%B2%A1_%E1%B2%9B%E1%B2%98%E1%B2%97%E1%B2%98%E1%B2%97%E1%B2%94%E1%B2%91%E1%B2%90.md).
- **სტრუქტურირებული წყარო აქტუალურია, მაგრამ ნათარგმნი ან მომლოდინე გამომავალი ძველია:** დიაგნოზის დასმა და არა მიწოდების საბოლოო წერტილი. შეინახეთ ორივე დროის შტამპი და შეამოწმეთ ანგარიში და გაგზავნის სტატუსი მიწოდების კონფიგურაციის შეცვლამდე.

<a id="5-follow-the-matching-branch"></a>
### 5. მიჰყევით შესაბამის ფილიალს

- არასრული იდენტიფიკაცია: [შეამოწმეთ გაუმართავი მოთამაშე](#map-an-unmapped-player).
- გამოტოვებული ყოველდღიური უწყვეტობა: [აღადგინეთ გამოტოვებული ყოველდღიური შეკრება](#restore-a-missing-daily-rollup).
- ცალსახად დამტკიცებული აღსრულების ტესტი არ წერდა: [დაადგინეთ დაბლოკილი Admin.ini ჩაწერეთ](#diagnose-a-blocked-adminini-write).
- ZIP მოპოვება ვერ მოხერხდა: [Windows-ის ამოღების შემთხვევის შეჯახების გადაჭრა](#resolve-a-windows-extraction-folder-collision).
- მოწყობილობის, პაკეტის ან საცავის შემოწმება ვერ მოხერხდა: [ვალიდაციის და გამოშვების მიმოხილვა](%E1%B2%95%E1%B2%90%E1%B2%9A%E1%B2%98%E1%B2%93%E1%B2%90%E1%B2%AA%E1%B2%98%E1%B2%90_%E1%B2%93%E1%B2%90_%E1%B2%92%E1%B2%90%E1%B2%9B%E1%B2%9D%E1%B2%A8%E1%B2%95%E1%B2%94%E1%B2%91%E1%B2%90.md#avoid-validation-environment-pitfalls).

<a id="6-stop-with-one-proved-outcome"></a>
### 6. შეაჩერე ერთი დადასტურებული შედეგი

პრობლემების მოგვარების საშვი სრულდება, როდესაც:

- მარშრუტი მიმდინარეა და `full`;
- მარშრუტი მიმდინარეა და `limited_expected_empty` დასახელებული მიზეზით;
- ჩაიწერება ერთი ზუსტი ბლოკერი, მტკიცებულების გზა და შემდეგი მოქმედება; ან
- უკან აღადგინა წინა ცნობილი მდგომარეობა და შეინარჩუნა წარუმატებელი მტკიცებულება.

„სერვერი მუშაობს“, მზარდი გულისცემა ან HTTP მხოლოდ წარმატება არ ადასტურებს ანგარიშის დასრულებას.

<a id="diagnose-a-missing-route"></a>
## გამოტოვებული მარშრუტის დიაგნოსტიკა

გახსენით `runtime/final_logs/route_proof.json` და შეადარე `server_status`, `daily_rollup`, `player_activity`, `case_review` და `critical_guard`.

1. წაიკითხეთ მარშრუტის მიზეზი, წარმომავლობა, გენერირების დრო და წყაროს მითითებები.
2. დაადასტურეთ, რომ დასახელებული სტრუქტურირებული წყარო არსებობს და მიეკუთვნება იმავე ციკლს.
3. შეადარეთ მისი mtime თარგმნილ გამომავალს და მომლოდინე კონვერტს.
4. თუ საბოლოო ჟურნალები უფრო ახალია, ვიდრე ნათარგმნი ან ელოდება გამომავალს, ჩაწერეთ სტაბილიზირებული დასრულების გაგზავნა და ჯერ შეაკეთეთ ეს გადაცემა.
5. თუ ყველა ადგილობრივი გამომავალი არის მიმდინარე, მაგრამ მიწოდება არ არის, მაშინ შეამოწმეთ მარშრუტის კონფიგურაცია და გამგზავნის სტატუსი.

არ დააწინაუროთ განრიგის ჯანმრთელობა ან ერთი წარმატებული შეტყობინება ხუთ მარშრუტზე.

<a id="interpret-incomplete-source-coverage"></a>
## არასრული წყაროს დაფარვის ინტერპრეტაცია

| მდგომარეობა | რა უნდა გავაკეთოთ |
|---|---|
| `partial` | გამოიყენეთ მხოლოდ შეგროვებული მტკიცებულებები და მოერიდეთ პრეტენზიებს სრული დაფარვის შესახებ. |
| `deferred` | კონფიგურაციის შეცვლამდე დაადასტურეთ მოგვიანებით შემოსაზღვრული სამუშაოები. |
| `unavailable` | ჩაწერეთ გარემოს ლიმიტი; შეასწორეთ მხოლოდ დადასტურებული გზა ან ნებართვის საკითხი. |
| `malformed` | შენახვა წყარო და გარჩევის შეცდომა; არ გამოიცნოთ დაკარგული მნიშვნელობები. |
| `permission_denied` | მხოლოდ საჭირო ვიწრო წაკითხვის ნებართვის მინიჭება. |
| `error` |  შეინახეთ დეტალები და დაადგინეთ დასახელებული ეტაპი მარშრუტზე დაყრდნობამდე. |

<a id="restore-missing-runtime-files"></a>
## აღადგინეთ დაკარგული დროის ფაილები

დაადასტურეთ:

```text
mods.txt contains RandomDayGuard : 1
RandomDayGuard/enabled.txt exists
RandomDayGuard/Scripts/main.lua exists
```

სწორი ინსტალაციის root არის:

```text
AbioticFactor/Binaries/Win64/ue4ss/Mods/RandomDayGuard/
```

უარი თქვით ამ ჩადგმულ განლაგებას:

```text
Mods/RandomDayGuard/RandomDayGuard/Scripts/main.lua
```

თუ ფაილები სწორია, მაგრამ UE4SS არ დაიწყო Guard, შეინახეთ `UE4SS.log` და შეადარეთ მისი გაშვების დროის ანაბეჭდი თამაშის პროცესის რეალურ დაწყებას.

<a id="resolve-a-windows-extraction-folder-collision"></a>
## Windows-ის ამოღების საქაღალდის შეჯახების გადაჭრა

ძველ გამოშვებაში გამოიყენებოდა პროგრამის დირექტორიები, რომელთა სახელები განსხვავდებოდა მხოლოდ კაპიტალიზაციით. Windows-ის ზოგიერთი ექსტრაქტორი აერთიანებს ამ სახელებს, როდესაც ZIP განთავსებულია არსებულ საქაღალდეზე.

1. წაშალეთ მხოლოდ წარუმატებელი დროებითი ამოღება და არა დაინსტალირებული მოდიფიკაცია ან მისი მტკიცებულება.
2. შექმენით ახალი ცარიელი დროებითი დირექტორია.
3. ამოიღეთ აქ მიმდინარე გამოშვება.
4. დაადასტურეთ, რომ ის აწარმოებს ერთ RandomDayGuard საქაღალდეს და ერთ პროგრამის დირექტორიას.
5. თუ Windows კვლავ იტყობინება შეჯახების შესახებ, ხელახლა ჩამოტვირთეთ გამოშვება და შეატყობინეთ გამოშვების ვერსიისა და გამოყენებული ექსტრაქტორის შესახებ.

არასოდეს ამოიღოთ ახალი გამოშვება დაინსტალირებული საქაღალდედან. მიჰყევით სუფთა საქაღალდის განახლების პროცედურას [`../INSTALL.md`](%E1%B2%98%E1%B2%9C%E1%B2%A1%E1%B2%A2%E1%B2%90%E1%B2%9A%E1%B2%90%E1%B2%AA%E1%B2%98%E1%B2%90.md).

```sh
grep -n "local VERSION" RandomDayGuard/Scripts/main.lua
cat RandomDayGuard/BUILD_MARKER.txt
```

თუ ისინი არ ეთანხმებიან:

1. გააჩერეთ სერვერი.
2. დაინსტალირებული საქაღალდის, განხილული კონფიგურაციისა და გაშვების მტკიცებულების სარეზერვო ასლის შექმნა.
3. დააყენეთ და შეამოწმეთ განკუთვნილი პაკეტი.
4. შეცვალეთ მხოლოდ პაკეტით მართული პროგრამა და მონაცემთა ფაილები.
5. დაადასტურეთ, რომ არსებობს კანონიკური ჩამტვირთავი და არ არის დამატებული პატარა დუბლიკატი.
6. დაიწყეთ ერთხელ და წაიკითხეთ მიმდინარე მარკერები, სანამ შეაფასებთ გაშვების დროს.

<a id="correct-a-missing-saved-root"></a>
## შეასწორეთ დაკარგული შენახული ფესვი

გახსენით `runtime/saved_path_probe.json`. დააყენეთ დამოწმებული აბსოლუტური გზა სრული აბიოტიკური ფაქტორისკენ `Saved/` დირექტორიაში `SavedRoot.txt`; არ მიუთითოთ მხოლოდ მსოფლიო დირექტორიაზე. ბილიკი შემოსაზღვრული ფესვის გარეთ უნდა დარჩეს უარყოფილი.

<a id="recover-a-stalled-historical-scan"></a>
## გაჩერებული ისტორიული სკანირების აღდგენა

მიმდინარე მონიტორინგი და ისტორიული აღმოჩენა ცალკეა. დიდ არქივს შეიძლება დასჭირდეს მრავალი შემოსაზღვრული ციკლი, ამიტომ ერთი უცვლელი დაკვირვება არ არის საკმარისი იმისათვის, რომ მას შეჩერებული ვუწოდოთ.

1. გახსენით `runtime/current/report_worker_status.json`.
2. ჩაწერა `scan_cursor`, აღმოჩენილი ფაილები, დასრულებული ფაილები და `last_progress_ts`.
3. დაელოდეთ მინიმუმ ორ ნორმალურ მოხსენების შესაძლებლობას და კვლავ შეადარეთ იგივე ველები.
4. თუ კურსორი, დასრულებული რაოდენობა ან პროგრესის დრო მიიწევს წინ, სკანირება კვლავ მუშაობს. დატოვე შემოსაზღვრული.
5. თუ პროგრესის ყველა ველი უცვლელი რჩება, სანამ გამოკითხვის ID და მიმდინარე ანგარიშები წინ მიიწევს, შეინახეთ სტატუსის ფაილი და შეამოწმეთ მუშაკის ფაზის მიერ დასახელებული წყაროს კლასი. ხელახლა ცდამდე შეაკეთეთ წყაროს გზა ან წაკითხვის წარუმატებლობა.

გაჩერებული ისტორიული სკანირება ზღუდავს დასკვნებს, რომლებიც საჭიროებენ ძველ ჩანაწერებს. ის არ არღვევს მიმდინარე მოხსენებას, რომლის აქტიური ჟურნალი და მიმდინარე ციკლის მტკიცებულება ახალია.

<a id="recover-a-stuck-poll-loop"></a>
## ჩარჩენილი გამოკითხვის ციკლის აღდგენა

გახსნა:

```text
runtime/current/poll_status.json
runtime/poll_error.txt
```

ჩაწერა `poll_id`, `poll_completed_count`, `poll_in_flight`, `poll_stage`, `scheduler_status` და დროის შტამპები ორჯერ შეზღუდული ინტერვალით.

- თუ მრიცხველები წინ მიიწევენ, მარყუჟი არ იჭედება; დაადგინეთ მუშაკის შემდგომი ეტაპი.
- თუ `poll_in_flight=true` უცვლელი რჩება, გადატვირთვამდე შეინახეთ პროგრესის ბოლო ეტაპი და შეცდომა.
- თუ დამგეგმავი შეჩერდა, შეამოწმეთ წინა შეცდომა და გაშვების გადაცემა.

არ დაამატოთ მეორე მარყუჟის მფლობელი ერთი შეფერხებული სასიცოცხლო ციკლის კომპენსაციისთვის.

<a id="start-the-scan-after-log-backlog"></a>
## დაიწყეთ სკანირება ჟურნალის ჩამორჩენის შემდეგ

ში `runtime/current/poll_status.json`, შეადარე:

```text
active_log_caught_up
active_log_unread_bytes
log_backlog_pending
```

ისტორიული სკანირება უნდა დაელოდოს, სანამ აქტიურ ჟურნალს აქვს წაუკითხავი ბაიტები. დაადასტურეთ, რომ მოგვიანებით გამოკითხვები შეამცირებს ჩამორჩენას. ფიქსირებული წაუკითხავი რაოდენობა წინსვლის გამოკითხვებით არის წყარო-კუდის პრობლემა; ფიქსირებული გამოკითხვა არის გრაფიკის პრობლემა.

<a id="preserve-scan-progress-after-a-crash"></a>
## შეინარჩუნეთ სკანირების პროგრესი ავარიის შემდეგ

შენახვა და შედარება:

```text
runtime/scan_checkpoint.json
runtime/scan_progress.json
runtime/baselines/file_manifest.tsv
```

გადაამოწმეთ, აკლია თუ არა საგუშაგო ან მანიფესტი, შეიცვალა თუ არა შენახული ფესვი ან სამყარო, თუ საგუშაგო მონიშნულია მოძველებული. არ წაშალოთ სწორი საბაზისო ხაზი, რათა პროგრესი უფრო ახალი გამოჩნდეს.

<a id="map-an-unmapped-player"></a>
## შეამოწმეთ გაუმართავი მოთამაშე

შეადარეთ სესიის მტკიცებულება ავტორიტეტულ ჟურნალს:

```text
runtime/evidence/session_events.jsonl
Saved/Logs/AbioticFactor.log
```

მოძებნეთ სრული `Login request` ურთიერთობა საჩვენებელ სახელს შორის, `ConnectID` და `UniqueId`. თუ არ არსებობს მიღებული კავშირის იდენტიფიკაცია, შეინახეთ მწკრივის მხოლოდ განხილვა. მხოლოდ საჩვენებელი სახელი ან PlayerData ფაილის სახელი არ არის შესასრულებელი იდენტობა.

<a id="diagnose-a-blocked-adminini-write"></a>
## დაადგინეთ დაბლოკილი Admin.ini ჩაწერეთ

გაატარეთ აღსრულების ტესტი მხოლოდ აშკარა დამტკიცებით და ერთჯერადი სატესტო ფაილით, არასოდეს ცოცხალი სერვერის ფაილით. ჯერ დაადასტურეთ, რომ სატესტო კონფიგურაცია მცველს სთხოვს დაწეროს:

```lua
review_only_mode = false
auto_ban = true
write_admin_ini = true
```

შემდეგ წაიკითხეთ ჩაწერილი წარუმატებლობის მიზეზი. მცველმა უნდა ამოიცნოს ერთი ანგარიში, დაიცვას მოდერატორები და სანდო ანგარიშები, მოძებნოს საკმარისი მტკიცებულება კონკრეტული ანგარიშისთვის, შექმნას და გადაამოწმოს ახალი სარეზერვო ასლი, დაადასტუროს, რომ არცერთმა პროგრამამ არ შეცვალა ფაილი, შეინახოს სავარაუდო განახლება და შეადაროს სრული შენახული ფაილი განზრახ შედეგს. თუ რომელიმე ნაბიჯი ვერ მოხერხდა ან მისი შემოწმება შეუძლებელია, დატოვეთ აკრძალვის სია უცვლელი. იხილეთ [Admin.ini აღსრულება](ADMIN_INI_ENFORCEMENT.md).

<a id="restore-a-missing-daily-rollup"></a>
## აღადგინეთ გამოტოვებული ყოველდღიური შეკრება

დაადასტურეთ `forensic_rollup.enabled = true`, შემდეგ შეამოწმეთ:

```text
runtime/current/forensic_today.json
runtime/forensic_days/YYYY-MM-DD/
runtime/final_logs/YYYY-MM-DD/
```

თუ ეს არ არის, შეამოწმეთ გაშვების, გამოკითხვის, ანგარიშის თანამშრომელი და წყაროს აღრიცხვის სტატუსი ამ თანმიმდევრობით. ყოველდღიური შეკრება არის ერთი უწყვეტი ჩანაწერი დღეში და არა სერვერის სტატუსის განმეორებითი შეტყობინება.
