<a id="worked-operation-examples"></a>
# ตัวอย่างการดำเนินงาน

> **แหล่งที่มาของภาษาอังกฤษตามรูปแบบบัญญัติ:** [EXAMPLE_RUNS.md](../../EXAMPLE_RUNS.md). เอกสารที่แปลเป็นภาษาท้องถิ่นนี้จะรักษาคำสั่ง เส้นทาง คีย์ ค่าสถานะ แฮช และชื่อไฟล์ที่แน่นอน หากถ้อยคำทางเทคนิคแตกต่างออกไป ให้ใช้ต้นฉบับภาษาอังกฤษ


ตัวอย่างเหล่านี้ใช้ค่าที่ประดิษฐ์ขึ้นเพื่ออธิบายการเปลี่ยนแปลงสถานะที่คาดหวัง ไม่ใช่ความเข้ากันได้แบบสดหรือหลักฐานของผู้เล่น

<a id="successful-current-cycle"></a>
## รอบปัจจุบันที่ประสบความสำเร็จ

อินพุต: บันทึกที่ใช้งานอยู่ที่สามารถอ่านได้, version/boot/epoch, `poll_id=41`, โพลปัจจุบันที่เสร็จสมบูรณ์, เขียนได้ accounting/history/report ราก, ไม่มีการบล็อกนโยบายการสแกนช้า

ที่คาดหวัง:

```text
server_status = full
player_activity = full or limited_expected_empty
case_review = full or limited_expected_empty
daily_rollup = full or limited_expected_empty
critical_guard = full or limited_expected_empty
```

ทุกเส้นทางที่เปิดใช้งานมี JSON/TXT เอาต์พุตและเชื้อสายเดียวกันใน `route_proof.json` สถานะเส้นทางขึ้นอยู่กับหัวเรื่องของตัวเอง ไม่ใช่ข้อความแสดงความสำเร็จทั่วไป

<a id="expected-empty-player-and-case-routes"></a>
## เส้นทางผู้เล่นว่างที่คาดหวังและเส้นทางเคส

อินพุต: การพิสูจน์วงจรปัจจุบันเสร็จสมบูรณ์ ไม่มีแถวผู้เล่นปัจจุบันหรือที่เก็บไว้ ไม่มีกรณีและปัญหาที่เก็บไว้และไม่มีบัญชี REVIEW/BAN-ELIGIBLE ปัจจุบัน

ที่คาดหวัง:

```text
player_activity.route_proof_status = limited_expected_empty
player_activity.expected_empty = true
player_activity.players = []

case_review.route_proof_status = limited_expected_empty
case_review.expected_empty = true
case_review.cases = []
```

รายงานที่แปลระบุว่าไม่พบหัวเรื่องที่มีขอบเขตที่มีสิทธิ์ พวกเขายังกล่าวอีกว่าสิ่งนี้ไม่ได้พิสูจน์ว่าไม่มีใครเคยเชื่อมต่อหรือไม่มีบริบทใดหายไป ไม่มีการสร้างตัวยึดตำแหน่ง player/case

<a id="partial-bounded-scan"></a>
## การสแกนขอบเขตบางส่วน

อินพุต: กระแสไฟใหม่ log/poll; `scan_checkpoint.json` หรือ `scan_progress.json` มีอยู่; การสแกนไม่สมบูรณ์ ค่าเริ่มต้น `slow_world_scan_blocks_current_reports=false`.

ที่คาดหวัง:

```text
world_save_scan.status = partial
source accounting = partial
server_status may still be full for fresh current state
historical routes name the scan limitation
```

ตั้งค่า `slow_world_scan_blocks_current_reports=true` เฉพาะเมื่อผู้ดำเนินการต้องการให้แหล่งที่มาที่ช้าซึ่งเป็นตัวเลือกนั้นบล็อกรายงานปัจจุบัน การกู้คืนคือการอนุญาตให้ผู้ปฏิบัติงานสแกนดำเนินการต่อ โดยไม่ต้องลบจุดตรวจสอบ

<a id="missing-current-cycle-proof"></a>
## ไม่มีหลักฐานรอบปัจจุบัน

อินพุต: บันทึกที่ใช้งานอยู่ไม่พร้อมใช้งาน `poll_id=0` หรือ boot/epoch/last-poll เชื้อสายหายไป

ที่คาดหวัง:

```text
current_cycle_proof_complete = false
all route proof statuses = missing
each configured route envelope status = suppressed_current_cycle
delivery_eligible = false
delivery_attempted = false
```

ซองจดหมายที่ถูกระงับเป็นบันทึกการตรวจสอบ ไม่ใช่การจัดส่งที่อยู่ในคิว บันทึกสุดท้ายเก่ายังคงเป็นประวัติศาสตร์เท่านั้น ซ่อมแซมฟิลด์ lineage/source แรกที่หายไปและสร้างวงจรที่ใหม่กว่า

<a id="malformed-optional-adminini-source"></a>
## ตัวเลือกที่มีรูปแบบไม่ถูกต้อง Admin.ini แหล่งที่มา

อินพุต: `Admin.ini` มีอยู่ แต่ล้มเหลวในการตรวจสอบความถูกต้องของโครงสร้าง

ที่คาดหวัง:

```text
admin_ini.status = malformed
source reference preserved
write/enforcement path closed
```

เก็บรักษาไฟล์และกู้คืนไฟล์ที่ตรวจสอบแล้ว รูปแบบที่สะอาด เก็บข้อความอธิบายไว้ในหลักฐานรันไทม์ `Admin.ini` รายการแบนแต่ละรายการยังคงอยู่เพียง `BannedPlayer=<ID>`.

<a id="required-active-log-probe-error"></a>
## ข้อผิดพลาดโพรบบันทึกที่ใช้งานอยู่ที่จำเป็น

อินพุต: โพรบบันทึกแอคทีฟที่จำเป็นที่มีขอบเขตล้มเหลวโดยมีข้อผิดพลาดในการอ่านที่ถูกสุขลักษณะ

ที่คาดหวัง:

```text
source_accounting.sources[active_log].status = error
source_accounting.sources[active_log].detail = "bounded active-log probe failed: <sanitized reason>"
coverage_status = unavailable
all route proof statuses = missing
```

`error` ยังคงอยู่ในแถวต้นทางโดยมีรายละเอียดที่มีขอบเขต รายงานระดับบนสุดใช้ `unavailable` และการพิสูจน์เส้นทางยังคงอยู่ `missing` จนกว่ารอบปัจจุบันที่ใหม่กว่าจะพิสูจน์แหล่งที่มาที่ต้องการ

<a id="incompatible-or-stale-baseline"></a>
## เข้ากันไม่ได้หรือข้อมูลพื้นฐานเก่า

อินพุต: เปลี่ยนแปลง package/source ข้อมูลประจำตัวหรือ stale/incompatible รายการพื้นฐาน

ที่คาดหวัง: การตรวจสอบหรือสถานะรันไทม์จะบันทึกความไม่เข้ากัน สถานะการสแกนไม่เรียกร้องให้มีการใช้ซ้ำโดยสมบูรณ์ เก็บรักษาหลักฐานก่อนหน้านี้ เริ่มการสร้างพื้นฐานใหม่อย่างชัดเจน และรอการพิสูจน์เทอร์มินัลใหม่ การบังคับให้สร้างใหม่โดยไม่มีเหตุผลบันทึกไว้ไม่ใช่การกู้คืนเริ่มต้น

<a id="paired-report-write-failure"></a>
## ความล้มเหลวในการเขียนรายงานที่จับคู่กัน

อินพุต: JSON เขียนสำเร็จ แต่ TXT เขียนล้มเหลว หรือกลับกัน

ที่คาดหวัง:

```text
route_proof_status = missing
completed = false
coverage_status = unavailable
output_write_detail = "paired JSON/TXT write failed: <sanitized reason>"
next_action = repair both route output writes
```

ความพยายามอย่างดีที่สุดของผู้เขียนจะเขียนพี่น้องทั้งสองใหม่เพื่อมาบรรจบกันเมื่อความล้มเหลว พี่น้องที่ประสบความสำเร็จหนึ่งคนไม่สามารถอยู่ในฐานะคำกล่าวอ้างความสำเร็จได้ รายละเอียดการเขียนที่มีขอบเขตไม่ได้สร้างค่าความครอบคลุมระดับบนสุดที่ห้า

<a id="route-proof-write-failure"></a>
## ความล้มเหลวในการเขียนเส้นทางที่พิสูจน์ได้

อินพุต: คู่เส้นทางถูกเขียน แต่ `route_proof.json` ไม่สามารถแทนที่ได้

ที่คาดหวัง: รายงานทั้งหมดจะถูกเขียนใหม่ `missing` ผลลัพธ์การแจ้งเตือนทั้งหมดจะถูกเขียนใหม่ `route_proof_write_failed` และไม่ยอมรับซองจดหมาย เส้นทางที่กำหนดค่าอาจมี `suppressed_current_cycle` ซองตรวจสอบที่มีแฟล็กการจัดส่งเป็นเท็จ ซ่อมแซมรากเอาต์พุตและสร้างวงจรปัจจุบันเดียวกันใหม่

<a id="review-only-enforcement-example"></a>
## ตัวอย่างการบังคับใช้เฉพาะการตรวจทานเท่านั้น

กำหนดค่า:

```lua
review_only_mode = true
auto_ban = false
write_admin_ini = false
```

คาดหวัง: อาจมีการเขียนคะแนน กรณีและปัญหา และคำแนะนำ `Admin.ini` ยังคงไม่เปลี่ยนแปลง นี่เป็นค่าเริ่มต้นสาธารณะ

<a id="approved-write-success-example"></a>
## ตัวอย่างความสำเร็จในการเขียนที่ได้รับอนุมัติ

เฉพาะการทดสอบที่ได้รับอนุมัติแยกต่างหากเท่านั้นที่สามารถตั้งค่าสวิตช์การเขียนทั้งสามตัวได้ นอกจากนี้ยังต้องพิสูจน์ตัวตนที่เป็นตัวเลขที่ชัดเจน trust/moderator การแยกออก เกณฑ์สิทธิ์ ถูกต้อง Admin.ini path/parse ความสำเร็จในการสำรองข้อมูล ความสำเร็จในการเขียน ความเท่าเทียมกันในการอ่านกลับ และหลักฐานเฉพาะบัญชี

ที่คาดหวัง:

```text
runtime/backups/Admin_<timestamp>_<source-fingerprint>_<clean-ID>.ini
Admin.ini contains one clean BannedPlayer=<ID>
runtime/enforced_bans.jsonl and evidence mirror record success
```

ตัวอย่างที่ประสบความสำเร็จไม่ได้เปิดใช้งานการบังคับใช้อัตโนมัติสำหรับบัญชีอื่น ๆ

<a id="writereadback-failure-with-rollback"></a>
## Write/readback ความล้มเหลวด้วยการย้อนกลับ

อินพุต: ทุกการเขียนล่วงหน้า ประตูผ่านไป; การเขียนทดแทนหรือการอ่านกลับล้มเหลว `rollback_on_readback_failure=true` และการสำรองข้อมูลที่ได้รับการยืนยันแล้วพร้อมใช้งาน

ที่คาดหวัง: หลักฐานความล้มเหลวบันทึกขั้นตอนและ `rollback_success`; ไบต์ Admin.ini ดั้งเดิมได้รับการกู้คืน และบัญชีไม่ได้รับการรายงานว่าบังคับใช้ได้สำเร็จ หากการย้อนกลับล้มเหลว ให้หยุดเขียน รักษาทั้ง files/evidence และกู้คืนด้วยตนเองจากการสำรองข้อมูล

<a id="local-outbox-example"></a>
## ตัวอย่างกล่องขาออกในเครื่อง

อินพุต: การแจ้งเตือนเปิดใช้งานในโหมด `local_file_outbox` เปิดใช้งานเส้นทาง พิสูจน์เส้นทางเสร็จสมบูรณ์ และ `full` หรืออนุญาตอย่างชัดเจน คาดว่าว่างเปล่า

ซองจดหมายที่คาดหวัง:

```text
schema = randomdayguard.notification/v1
completed_output = true
status = ready_for_local_consumer
delivery_eligible = true
delivery_backend = none
delivery_attempted = false
```

สำหรับ missing/ineligible เอาต์พุต เส้นทางเดียวกันอาจมี `status=suppressed_current_cycle`, `completed_output=false` และ `delivery_eligible=false` แทน ไฟล์ใดไฟล์หนึ่งพิสูจน์ว่ามีการเขียนในเครื่องเท่านั้น ไม่มีผู้ให้บริการ การขนส่ง การจัดส่ง หรือใบรับการอ่านรวมกลุ่มหรืออนุมาน
