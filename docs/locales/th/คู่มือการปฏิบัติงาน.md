# Playbook การดำเนินการ

> **แหล่งที่มาของภาษาอังกฤษตามรูปแบบบัญญัติ:** [OPERATIONS_PLAYBOOK.md](../../OPERATIONS_PLAYBOOK.md). เอกสารที่แปลเป็นภาษาท้องถิ่นนี้จะรักษาคำสั่ง เส้นทาง คีย์ ค่าสถานะ แฮช และชื่อไฟล์ที่แน่นอน หากถ้อยคำทางเทคนิคแตกต่างออกไป ให้ใช้ต้นฉบับภาษาอังกฤษ


นี่คือลำดับการอ่านปกติสำหรับ RandomDayGuard คุณไม่จำเป็นต้องรู้ JSON, Git, checksums หรือเครื่องมือบรรทัดคำสั่งเพื่อตรวจสอบเซิร์ฟเวอร์ที่มีประสิทธิภาพ

<a id="daily-operator-flow"></a>
## โฟลว์ตัวดำเนินการรายวัน

1. เปิด `runtime/final_logs/server_status_latest.txt` โดยจะบอกคุณว่า Guard กำลังติดตามการทำงานของเซิร์ฟเวอร์ปัจจุบันหรือไม่ เมื่อรอบสุดท้ายเสร็จสิ้น จำนวนผู้เล่นที่เชื่อมต่อ และแหล่งที่มาหรือการสแกนไม่สมบูรณ์หรือไม่
2. เปิด `runtime/final_logs/daily_rollup_latest.txt` วันละครั้ง โดยสรุปเซสชันในวันเดียวกัน การออก งานกรณีที่มีชื่อ รายการข้อมูลประจำตัว และความครอบคลุมของแหล่งที่มาโดยไม่ต้องทำซ้ำทุกบันทึก
3. เปิด `runtime/final_logs/player_activity_latest.txt` เฉพาะเมื่อเซิร์ฟเวอร์มีการเข้าร่วม ออก หรือเซสชันที่ใช้งานอยู่ในระหว่างวัน
4. เปิด `runtime/final_logs/case_review_latest.txt` เฉพาะเมื่อตั้งชื่อหัวข้อปัจจุบันเท่านั้น รายงานจะให้บัญชี สถานะการตรวจสอบ คะแนน แหล่งที่มาของข้อมูลประจำตัว และบันทึกเพื่อเปิดถัดไป
5. เปิด `runtime/final_logs/critical_guard_latest.txt` เฉพาะเมื่อ Guard รายงานความล้มเหลวในการเริ่มต้น รอบการตรวจสอบ หรือการเขียนรายงานของตนเอง

หากเส้นทางไม่มีอะไรจะรายงาน Guard จะบันทึกผลลัพธ์ที่ว่างเปล่าที่คาดไว้ นั่นคือการตรวจสอบที่เสร็จสมบูรณ์ ไม่ใช่รายงานที่ขาดหายไป

<a id="what-to-read-inside-a-report"></a>
## สิ่งที่ต้องอ่านในรายงาน

อ่านส่วนเหล่านี้ตามลำดับ:

1. **สรุป** - รายงานนี้ครอบคลุมถึงอะไรบ้าง
2. **สิ่งที่เจ้าหน้าที่เฝ้าสังเกต** - การประทับเวลาจริง จำนวน บัญชี เซสชัน หรือค่าสถานะที่รวบรวมสำหรับเส้นทางนี้
3. **มันหมายถึงอะไร** - การตีความบันทึกเหล่านั้นด้วยภาษาธรรมดา
4. **สิ่งที่ยังไม่ทราบ** - แหล่งที่มาหรือขีดจำกัดการสแกนที่ส่งผลต่อผลลัพธ์
5. **แนะนำขั้นตอนต่อไป** - ไม่ว่าจะตรวจสอบ ตรวจสอบหัวข้อที่มีชื่อ หรือซ่อมแซม Guard
6. **ขอบเขตหลักฐาน** - ขีดจำกัดขอบเขตของรายงาน

บันทึกทางเทคนิคและการอ้างอิงแหล่งที่มาจะปรากฏที่ส่วนท้ายสำหรับผู้อ่านที่ต้องการตรวจสอบหลักฐานที่มีโครงสร้างที่แน่นอน

<a id="when-a-report-is-missing"></a>
## เมื่อรายงานหายไป

เปิด `runtime/final_logs/route_proof.json` เฉพาะเมื่อไม่มีรายงานที่อ่านได้หรือบอกว่าหลักฐานปัจจุบันขาดหายไป แต่ละเส้นทางมีผลลัพธ์อย่างใดอย่างหนึ่งต่อไปนี้:

| ผลลัพธ์ | ความหมาย |
|---|---|
| `full` | Guard เสร็จสิ้นเส้นทางด้วยหลักฐานที่เป็นเจ้าของเส้นทางในปัจจุบัน |
| `limited_expected_empty` | Guard เสร็จสิ้นเส้นทางและไม่พบเหตุการณ์ที่เข้าเกณฑ์ หรือบันทึกขีดจำกัดวุฒิภาวะที่ระบุชื่อ |
| `missing` | แหล่งที่มาที่จำเป็น การตรวจสอบเชื้อสาย หรือการเขียนรายงานที่จับคู่ไม่เสร็จสมบูรณ์ |

สำหรับเส้นทางที่ขาดหายไป ให้ติดตามแหล่งที่มาที่มีชื่อหรือเขียนข้อผิดพลาดในรายงาน อย่าเปลี่ยนเส้นทางหรือการตั้งค่าการแจ้งเตือนที่ไม่เกี่ยวข้องก่อน

<a id="after-a-crash-or-restart"></a>
## หลังจากเกิดข้อขัดข้องหรือรีสตาร์ท

1. อ่านสถานะเซิร์ฟเวอร์สำหรับการประทับเวลาการทำงานของเซิร์ฟเวอร์ใหม่และรอบการตรวจสอบที่เสร็จสมบูรณ์ล่าสุด
2. อ่าน Critical Guard สำหรับการเริ่มต้นระบบปัจจุบันหรือความล้มเหลวในการโพล
3. อ่านกิจกรรมของผู้เล่นเฉพาะในกรณีที่เซสชันในวันเดียวกันเข้าร่วม ออกจาก หรือส่งคืนหลังจากการเปลี่ยนแปลงวงจรชีวิต
4. เก็บรักษาบันทึกแหล่งที่มาที่อ้างถึงก่อนที่จะเปลี่ยนการกำหนดค่า

<a id="before-enabling-optional-adminini-writes"></a>
## ก่อนที่จะเปิดใช้งานตัวเลือก Admin.ini เขียน

แพ็คเกจเริ่มต้นจะเฝ้าดูและรายงานโดยไม่มีการเปลี่ยนแปลง `Admin.ini`. ตัวดำเนินการขั้นสูงสามารถเปิดใช้งานเส้นทางการบังคับใช้ทางเลือกได้หลังจากทดสอบกับสำเนาของไฟล์แล้ว Guard จึงต้องการ ID บัญชีที่เป็นตัวเลขที่สะอาด ปกป้องบัญชีที่เชื่อถือได้ สร้างและยืนยันการสำรองข้อมูล ปฏิเสธการเปลี่ยนแปลงที่เกิดขึ้นพร้อมกัน อ่านไฟล์ที่บันทึกไว้กลับ และกู้คืนข้อมูลสำรองหากการตรวจสอบล้มเหลว ดู [`ADMIN_INI_ENFORCEMENT.md`](ADMIN_INI_%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%9A%E0%B8%B1%E0%B8%87%E0%B8%84%E0%B8%B1%E0%B8%9A%E0%B9%83%E0%B8%8A%E0%B9%89.md) สำหรับการตั้งค่าและขั้นตอนการทดสอบที่สมบูรณ์
