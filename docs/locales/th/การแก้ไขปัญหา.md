# การแก้ไขปัญหา

> **แหล่งที่มาของภาษาอังกฤษตามรูปแบบบัญญัติ:** [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md). เอกสารที่แปลเป็นภาษาท้องถิ่นนี้จะรักษาคำสั่ง เส้นทาง คีย์ ค่าสถานะ แฮช และชื่อไฟล์ที่แน่นอน หากถ้อยคำทางเทคนิคแตกต่างออกไป ให้ใช้ต้นฉบับภาษาอังกฤษ


ใช้หน้านี้เมื่อ Guard ไม่โหลด ไม่สามารถรวบรวมแหล่งที่มาได้ รายงานไม่ปรากฏขึ้น หรือหลักฐานเส้นทางขัดแย้งกับสิ่งที่คุณคาดหวัง เริ่มต้นด้วยแผนผังการตัดสินใจและติดตามสาขาเดียว ใช้ [สถานะและการอ้างอิงข้อผิดพลาด](%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%AD%E0%B9%89%E0%B8%B2%E0%B8%87%E0%B8%AD%E0%B8%B4%E0%B8%87%E0%B8%AA%E0%B8%96%E0%B8%B2%E0%B8%99%E0%B8%B0%E0%B9%81%E0%B8%A5%E0%B8%B0%E0%B8%82%E0%B9%89%E0%B8%AD%E0%B8%9C%E0%B8%B4%E0%B8%94%E0%B8%9E%E0%B8%A5%E0%B8%B2%E0%B8%94.md) เฉพาะหลังจากที่ทราบเลเยอร์ที่ล้มเหลวแล้วเท่านั้น

เก็บรักษาไฟล์รันไทม์ปัจจุบันก่อนที่จะเปลี่ยนการกำหนดค่าหรือติดตั้งใหม่ อาร์ติแฟกต์ที่เก่าหรือหายไปจะระบุถึงขั้นตอนที่ล้มเหลว การรีสตาร์ทซ้ำหลายครั้งสามารถลบหลักฐานนั้นได้

<a id="choose-the-failure-path"></a>
## เลือกเส้นทางความล้มเหลว

<a id="1-decide-whether-guard-loaded"></a>
### 1. ตัดสินใจว่า Guard โหลดแล้ว

- **ไม่มีไฟล์ `runtime/` อยู่:** ติดตาม [กู้คืนไฟล์รันไทม์ที่หายไป](#restore-missing-runtime-files) ตรวจสอบเส้นทางการติดตั้ง, ตัวโหลด Canonical, `enabled.txt` และ `mods.txt` ก่อนที่จะตรวจสอบรายงาน
- **มีไฟล์สถานะปัจจุบัน:** Guard โหลดมากพอที่จะเขียนสถานะได้ ดำเนินการต่อไปยังขั้นตอนที่ 2; การติดตั้งใหม่ไม่ใช่การตอบสนองครั้งแรก

<a id="2-decide-whether-the-scheduler-is-advancing"></a>
### 2. ตัดสินใจว่าตัวกำหนดเวลากำลังก้าวหน้าหรือไม่

เปิด:

```text
runtime/current/startup_status.json
runtime/current/poll_status.json
```

- **ตัวนับและการประทับเวลาล่วงหน้า:** ดำเนินการต่อไปยังขั้นตอนที่ 3
- **`poll_id` เป็นแบบคงที่ `poll_in_flight` ยังคงเป็นจริง หรือสถานะตัวกำหนดเวลาไม่ทำงาน:** ติดตาม [กู้คืนลูปโพลที่ค้างอยู่](#recover-a-stuck-poll-loop).
- **การสแกนพื้นฐานอยู่ระหว่างดำเนินการในขณะที่ความคืบหน้าของตัวกำหนดเวลาดำเนินต่อไป:** นี่เป็นข้อควรระวัง ไม่ใช่การเริ่มต้นล้มเหลวโดยอัตโนมัติ ตรวจสอบเฉพาะในกรณีที่ความคืบหน้าของ Backlog หรือการสแกนหยุดลง

<a id="3-classify-route-proof"></a>
### 3. แยกประเภทการพิสูจน์เส้นทาง

เปิด `runtime/final_logs/route_proof.json` และตรวจสอบทุกเส้นทาง แยกกัน

- **`full`:** เปรียบเทียบถ้อยคำที่ไม่คาดคิดกับปัจจุบัน `source_references` และเชื้อสายปัจจุบัน อย่าเปลี่ยนการจัดส่งเนื่องจากถ้อยคำเพียงอย่างเดียวดูผิด
- **`limited_expected_empty`:** ยืนยันว่าการบัญชีต้นทางสนับสนุนผลลัพธ์ที่ว่างเปล่าที่ถูกต้องตามกฎหมาย อย่าสร้างเครื่องเล่นหรือเคสสังเคราะห์
- **`missing`:** ติดตาม [วินิจฉัยเส้นทางที่หายไป](#diagnose-a-missing-route).

<a id="4-classify-source-coverage"></a>
### 4. จำแนกประเภทความครอบคลุมของแหล่งที่มา

- **`partial`, `deferred`, `unavailable`, `malformed`, `permission_denied` หรือ `error`:** ติดตาม [ตีความความครอบคลุมของแหล่งที่มาที่ไม่สมบูรณ์](#interpret-incomplete-source-coverage) จากนั้นค้นหาโค้ดที่ถูกต้องใน [การอ้างอิงสถานะและข้อผิดพลาด](%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%AD%E0%B9%89%E0%B8%B2%E0%B8%87%E0%B8%AD%E0%B8%B4%E0%B8%87%E0%B8%AA%E0%B8%96%E0%B8%B2%E0%B8%99%E0%B8%B0%E0%B9%81%E0%B8%A5%E0%B8%B0%E0%B8%82%E0%B9%89%E0%B8%AD%E0%B8%9C%E0%B8%B4%E0%B8%94%E0%B8%9E%E0%B8%A5%E0%B8%B2%E0%B8%94.md).
- **แหล่งที่มาที่มีโครงสร้างเป็นปัจจุบัน แต่เอาต์พุตที่แปลหรือรอดำเนินการเก่ากว่า:** วินิจฉัยแฮนด์ออฟที่เสร็จสมบูรณ์ ไม่ใช่จุดสิ้นสุดการจัดส่ง รักษาทั้งการประทับเวลาและตรวจสอบรายงานและสถานะการจัดส่งก่อนที่จะเปลี่ยนการกำหนดค่าการจัดส่ง

<a id="5-follow-the-matching-branch"></a>
### 5. ติดตามสาขาที่ตรงกัน

- ข้อมูลประจำตัวที่ไม่สมบูรณ์: [แมปโปรแกรมเล่นที่ยังไม่ได้แมป](#map-an-unmapped-player).
- ขาดความต่อเนื่องรายวัน: [กู้คืนรายงานสรุปรายวันที่หายไป](#restore-a-missing-daily-rollup).
- การทดสอบการบังคับใช้ที่ได้รับอนุมัติอย่างชัดเจนไม่ได้เขียน: [วินิจฉัย Admin.ini การเขียนที่ถูกบล็อก](#diagnose-a-blocked-adminini-write).
- ZIP การแยกล้มเหลว: [แก้ไขการชนกันของเคสการแยก Windows](#resolve-a-windows-extraction-folder-collision).
- การตรวจสอบโปรแกรมติดตั้ง แพ็กเกจ หรือที่เก็บข้อมูลล้มเหลว: [การตรวจสอบความถูกต้องและการทบทวนการเปิดตัว](%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%95%E0%B8%A3%E0%B8%A7%E0%B8%88%E0%B8%AA%E0%B8%AD%E0%B8%9A%E0%B8%84%E0%B8%A7%E0%B8%B2%E0%B8%A1%E0%B8%96%E0%B8%B9%E0%B8%81%E0%B8%95%E0%B9%89%E0%B8%AD%E0%B8%87%E0%B9%81%E0%B8%A5%E0%B8%B0%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B9%80%E0%B8%9C%E0%B8%A2%E0%B9%81%E0%B8%9E%E0%B8%A3%E0%B9%88.md#avoid-validation-environment-pitfalls).

<a id="6-stop-with-one-proved-outcome"></a>
### 6. หยุดด้วยผลลัพธ์ที่พิสูจน์แล้วเพียงผลลัพธ์เดียว

การส่งผ่านการแก้ไขปัญหาสิ้นสุดลง เมื่อ:

- เส้นทางเป็นปัจจุบันและ `full`;
- เส้นทางเป็นปัจจุบันและ `limited_expected_empty` ด้วยเหตุผลที่ระบุชื่อ
- ตัวบล็อกที่แน่นอน เส้นทางหลักฐาน และการดำเนินการถัดไปจะถูกบันทึก หรือ
- การย้อนกลับคืนค่าสถานะที่ทราบก่อนหน้านี้และรักษาหลักฐานที่ล้มเหลว

“เซิร์ฟเวอร์กำลังทำงาน” การเต้นของหัวใจที่เพิ่มขึ้นหรือความสำเร็จ HTTP เพียงอย่างเดียวไม่ได้พิสูจน์ว่าเส้นทางรายงานเสร็จสมบูรณ์

<a id="diagnose-a-missing-route"></a>
## วินิจฉัยเส้นทางที่หายไป

เปิด `runtime/final_logs/route_proof.json` และเปรียบเทียบ `server_status`, `daily_rollup`, `player_activity`, `case_review` และ `critical_guard`.

1. อ่านเหตุผล เส้นทาง สายเลือด เวลาในการสร้าง และแหล่งที่มา การอ้างอิง
2. ยืนยันว่ามีแหล่งที่มาที่มีโครงสร้างที่มีชื่ออยู่และเป็นของรอบเดียวกัน
3. เปรียบเทียบ mtime ของมันกับเอาต์พุตที่แปลและซองจดหมายที่รอดำเนินการ
4. หากบันทึกสุดท้ายใหม่กว่าการแปลหรือเอาต์พุตที่รอดำเนินการ ให้บันทึกการจัดส่งที่เสร็จสมบูรณ์แล้วและซ่อมแซมแฮนด์ออฟนั้นก่อน
5. หากเอาต์พุตในเครื่องทั้งหมดเป็นปัจจุบันแต่ไม่มีการส่งมอบ จากนั้นตรวจสอบการกำหนดค่าเส้นทางและสถานะผู้ส่ง

อย่าส่งเสริมความสมบูรณ์ของตัวกำหนดตารางเวลาหรือการแจ้งเตือนที่ประสบความสำเร็จเพียงครั้งเดียวต่อการพิสูจน์เส้นทางห้าเส้นทาง

<a id="interpret-incomplete-source-coverage"></a>
## ตีความความครอบคลุมของแหล่งที่มาที่ไม่สมบูรณ์

| สถานะ | ต้องทำอย่างไร |
|---|---|
| `partial` | ใช้เฉพาะหลักฐานที่รวบรวมไว้และหลีกเลี่ยงการอ้างสิทธิ์ที่ครอบคลุมทั้งหมด |
| `deferred` | ยืนยันความก้าวหน้างานที่มีขอบเขตในภายหลังก่อน การเปลี่ยนการกำหนดค่า |
| `unavailable` | บันทึกขีดจำกัดของสภาพแวดล้อม แก้ไขเฉพาะเส้นทางที่พิสูจน์แล้วหรือปัญหาการอนุญาต |
| `malformed` | รักษาแหล่งที่มาและข้อผิดพลาดในการแยกวิเคราะห์ อย่าเดาค่าที่หายไป |
| `permission_denied` | ให้สิทธิ์การอ่านแบบแคบที่จำเป็นเท่านั้น |
| `error` | เก็บรักษารายละเอียดและวินิจฉัยสเตจที่มีชื่อก่อนที่จะใช้เส้นทาง |

<a id="restore-missing-runtime-files"></a>
## กู้คืนไฟล์รันไทม์ที่หายไป

ยืนยัน:

```text
mods.txt contains RandomDayGuard : 1
RandomDayGuard/enabled.txt exists
RandomDayGuard/Scripts/main.lua exists
```

รูทการติดตั้งที่ถูกต้องคือ:

```text
AbioticFactor/Binaries/Win64/ue4ss/Mods/RandomDayGuard/
```

ปฏิเสธเค้าโครงที่ซ้อนกันนี้:

```text
Mods/RandomDayGuard/RandomDayGuard/Scripts/main.lua
```

หากไฟล์ถูกต้อง แต่ UE4SS ไม่ได้เริ่ม Guard ให้คงไว้ `UE4SS.log` และเปรียบเทียบการประทับเวลาเริ่มต้นกับการเริ่มกระบวนการเกมจริง

<a id="resolve-a-windows-extraction-folder-collision"></a>
## แก้ไขการชนกันของโฟลเดอร์แยก Windows

รุ่นเก่าใช้ไดเร็กทอรีโปรแกรมซึ่งมีชื่อต่างกันเพียงตัวพิมพ์ใหญ่เท่านั้น ตัวแยกข้อมูล Windows บางตัวจะรวมชื่อเหล่านั้นเมื่อวาง ZIP ไว้เหนือโฟลเดอร์ที่มีอยู่

1. ลบเฉพาะการแตกไฟล์ชั่วคราวที่ไม่สำเร็จเท่านั้น ไม่ใช่ม็อดที่ติดตั้งหรือหลักฐาน
2. สร้างไดเรกทอรีชั่วคราวที่ว่างเปล่าใหม่
3. แยกรุ่นปัจจุบันออกจากที่นั่น
4. ยืนยันว่าสร้างโฟลเดอร์ RandomDayGuard หนึ่งโฟลเดอร์และหนึ่งไดเรกทอรีโปรแกรม
5. หาก Windows ยังคงรายงานการชนกัน ให้ดาวน์โหลดรุ่นอีกครั้งและรายงานรุ่นวางจำหน่ายและเครื่องมือแยกที่ใช้

ไม่ต้องแตกไฟล์ใหม่ออกจากโฟลเดอร์ที่ติดตั้ง ปฏิบัติตามขั้นตอนการอัปเดตโฟลเดอร์ใหม่ทั้งหมดใน [`../INSTALL.md`](%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%95%E0%B8%B4%E0%B8%94%E0%B8%95%E0%B8%B1%E0%B9%89%E0%B8%87.md).

<a id="load-the-expected-version"></a>
## โหลดเวอร์ชันที่ต้องการ

ตรวจสอบเครื่องหมายแหล่งที่มาและเครื่องหมายการสร้าง:

```sh
grep -n "local VERSION" RandomDayGuard/Scripts/main.lua
cat RandomDayGuard/BUILD_MARKER.txt
```

หากพวกเขาไม่เห็นด้วย:

1. หยุดเซิร์ฟเวอร์
2. สำรองข้อมูลโฟลเดอร์ที่ติดตั้ง ตรวจสอบการกำหนดค่า และหลักฐานรันไทม์
3. ดำเนินการและตรวจสอบแพ็คเกจที่ต้องการ
4. แทนที่เฉพาะโปรแกรมที่จัดการแพ็คเกจและไฟล์ข้อมูล
5. ยืนยันว่ามีตัวโหลด Canonical อยู่ และไม่มีการเพิ่มตัวพิมพ์เล็กที่ซ้ำกัน
6. เริ่มต้นหนึ่งครั้งและอ่านกลับเครื่องหมายปัจจุบันก่อนที่จะตัดสินเอาต์พุตรันไทม์

<a id="correct-a-missing-saved-root"></a>
## แก้ไขรูทที่บันทึกไว้ที่หายไป

เปิด `runtime/saved_path_probe.json`. ใส่เส้นทางสัมบูรณ์ที่ได้รับการยืนยันแล้วไปยังปัจจัยทางชีวะที่สมบูรณ์ `Saved/` นั้นใน `SavedRoot.txt`; อย่าชี้ไปที่ไดเร็กทอรีโลกเท่านั้น เส้นทางที่อยู่นอกรูทที่มีขอบเขตจะต้องถูกปฏิเสธต่อไป

<a id="recover-a-stalled-historical-scan"></a>
## กู้คืนการสแกนประวัติที่ค้างอยู่

การตรวจสอบปัจจุบันและการค้นพบในอดีตจะแยกจากกัน ไฟล์เก็บถาวรขนาดใหญ่อาจต้องใช้วงจรที่มีขอบเขตจำกัด ดังนั้นการสังเกตที่ไม่เปลี่ยนแปลงเพียงครั้งเดียวจึงไม่เพียงพอที่จะหยุดการทำงาน

1. เปิด `runtime/current/report_worker_status.json`.
2. บันทึก `scan_cursor`, ไฟล์ที่ค้นพบ, ไฟล์ที่เสร็จสมบูรณ์ และ `last_progress_ts`.
3. รออย่างน้อยสองโอกาสของผู้ปฏิบัติงานรายงานตามปกติแล้วเปรียบเทียบฟิลด์เดียวกันอีกครั้ง
4. หากเคอร์เซอร์ การนับเสร็จสมบูรณ์ หรือเวลาความคืบหน้าเลื่อนไปข้างหน้า การสแกนจะยังคงทำงานอยู่ ปล่อยให้มีขอบเขต
5. หากฟิลด์ความคืบหน้าทั้งหมดยังคงไม่เปลี่ยนแปลงในขณะที่รหัสโพลและรายงานปัจจุบันยังคงดำเนินต่อไป ให้เก็บไฟล์สถานะไว้และตรวจสอบคลาสต้นทางที่ตั้งชื่อตามเฟสของผู้ปฏิบัติงาน ซ่อมแซมเส้นทางต้นทางหรือการอ่านล้มเหลวก่อนลองอีกครั้ง

การสแกนประวัติที่หยุดชะงักจะจำกัดข้อสรุปที่ต้องใช้บันทึกที่เก่ากว่า ไม่ได้ทำให้รายงานปัจจุบันเป็นโมฆะซึ่งมีการพิสูจน์บันทึกที่ใช้งานอยู่และรอบปัจจุบันเป็นปัจจุบัน

<a id="recover-a-stuck-poll-loop"></a>
## กู้คืนลูปโพลที่ค้างอยู่

เปิด:

```text
runtime/current/poll_status.json
runtime/poll_error.txt
```

บันทึก `poll_id`, `poll_completed_count`, `poll_in_flight`, `poll_stage`, `scheduler_status` และประทับเวลาสองครั้งในช่วงเวลาที่มีขอบเขต

- หากตัวนับล่วงหน้า การวนซ้ำจะไม่ค้าง วินิจฉัยขั้นตอนของผู้ปฏิบัติงานในภายหลัง
- หาก `poll_in_flight=true` ยังคงไม่เปลี่ยนแปลง ให้รักษาขั้นตอนความคืบหน้าล่าสุดและข้อผิดพลาดก่อนที่จะรีสตาร์ท
- หากตัวกำหนดเวลาหยุด ให้ตรวจสอบข้อผิดพลาดก่อนหน้าและแฮนด์ออฟการเริ่มต้นระบบ

อย่าเพิ่มเจ้าของลูปที่สองเพื่อชดเชยวงจรชีวิตที่หยุดชะงักหนึ่งรอบ

<a id="start-the-scan-after-log-backlog"></a>
## เริ่มการสแกนหลังจากบันทึกงานที่ค้างอยู่

ใน `runtime/current/poll_status.json` ให้เปรียบเทียบ:

```text
active_log_caught_up
active_log_unread_bytes
log_backlog_pending
```

การสแกนประวัติควรรอในขณะที่บันทึกที่ใช้งานอยู่มีไบต์ที่ยังไม่ได้อ่าน ยืนยันโพลภายหลังลดยอดค้าง จำนวนที่ยังไม่ได้อ่านคงที่พร้อมกับโพลที่ก้าวหน้าคือปัญหาแหล่งที่มา การสำรวจความคิดเห็นแบบคงที่เป็นปัญหาของตัวกำหนดเวลา

<a id="preserve-scan-progress-after-a-crash"></a>
## รักษาความคืบหน้าในการสแกนหลังจากเกิดข้อขัดข้อง

เก็บรักษาและเปรียบเทียบ:

```text
runtime/scan_checkpoint.json
runtime/scan_progress.json
runtime/baselines/file_manifest.tsv
```

ตรวจสอบว่าจุดตรวจสอบหรือรายการหายไป รากที่บันทึกไว้หรือโลกเปลี่ยนไป หรือจุดตรวจสอบถูกทำเครื่องหมายว่าไม่มีการอัปเดต อย่าลบพื้นฐานที่ถูกต้องเพื่อให้ความคืบหน้าปรากฏใหม่

<a id="map-an-unmapped-player"></a>
## แมปโปรแกรมเล่นที่ยังไม่ได้แมป

เปรียบเทียบหลักฐานเซสชันกับบันทึกที่เชื่อถือได้:

```text
runtime/evidence/session_events.jsonl
Saved/Logs/AbioticFactor.log
```

มองหาความสัมพันธ์ `Login request` ที่สมบูรณ์ระหว่างชื่อที่แสดง `ConnectID` และ `UniqueId` หากไม่มีข้อมูลระบุตัวตนการเชื่อมต่อที่ยอมรับ ให้เก็บแถวไว้เพื่อการตรวจทานเท่านั้น ชื่อที่แสดงหรือ PlayerData ชื่อไฟล์เพียงอย่างเดียวไม่ใช่ข้อมูลระบุตัวตนที่สามารถบังคับใช้ได้

<a id="diagnose-a-blocked-adminini-write"></a>
## วินิจฉัย Admin.ini การเขียนที่ถูกบล็อก

เรียกใช้การทดสอบการบังคับใช้เฉพาะเมื่อได้รับอนุมัติอย่างชัดเจนและไฟล์ทดสอบแบบใช้แล้วทิ้ง ไม่ใช้กับไฟล์เซิร์ฟเวอร์ที่ใช้งานจริง ขั้นแรกให้ยืนยันว่าการกำหนดค่าการทดสอบขอให้ Guard เขียน:

```lua
review_only_mode = false
auto_ban = true
write_admin_ini = true
```

จากนั้นอ่านเหตุผลความล้มเหลวที่บันทึกไว้ Guard ต้องระบุบัญชีเดียว ปกป้องผู้ดูแลและบัญชีที่เชื่อถือได้ ค้นหาหลักฐานเฉพาะบัญชีที่เพียงพอ สร้างและตรวจสอบการสำรองข้อมูลใหม่ ยืนยันว่าไม่มีโปรแกรมอื่นเปลี่ยนแปลงไฟล์ บันทึกการอัปเดตที่ต้องการ และเปรียบเทียบไฟล์ที่บันทึกไว้ทั้งหมดกับผลลัพธ์ที่ต้องการ หากขั้นตอนใดล้มเหลวหรือไม่สามารถตรวจสอบได้ ให้ปล่อยรายการแบนไว้เท่าเดิม ดู [Admin.ini การบังคับใช้](ADMIN_INI_%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%9A%E0%B8%B1%E0%B8%87%E0%B8%84%E0%B8%B1%E0%B8%9A%E0%B9%83%E0%B8%8A%E0%B9%89.md).

<a id="restore-a-missing-daily-rollup"></a>
## กู้คืนรายงานสรุปรายวันที่หายไป

ยืนยัน `forensic_rollup.enabled = true` จากนั้นตรวจสอบ:

```text
runtime/current/forensic_today.json
runtime/forensic_days/YYYY-MM-DD/
runtime/final_logs/YYYY-MM-DD/
```

หากข้อมูลเหล่านี้หายไป ให้ตรวจสอบสถานะการเริ่มต้นระบบ การสำรวจความคิดเห็น ผู้ปฏิบัติงานรายงาน และสถานะบัญชีต้นทางตามลำดับดังกล่าว การรวบรวมรายวันคือบันทึกความต่อเนื่องหนึ่งรายการต่อวัน ไม่ใช่การแจ้งเตือนสถานะเซิร์ฟเวอร์ซ้ำ

<a id="look-up-an-exact-status-or-error"></a>
## ค้นหาสถานะหรือข้อผิดพลาดที่แน่นอน

ใช้ [การอ้างอิงสถานะและข้อผิดพลาด](%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%AD%E0%B9%89%E0%B8%B2%E0%B8%87%E0%B8%AD%E0%B8%B4%E0%B8%87%E0%B8%AA%E0%B8%96%E0%B8%B2%E0%B8%99%E0%B8%B0%E0%B9%81%E0%B8%A5%E0%B8%B0%E0%B8%82%E0%B9%89%E0%B8%AD%E0%B8%9C%E0%B8%B4%E0%B8%94%E0%B8%9E%E0%B8%A5%E0%B8%B2%E0%B8%94.md) สำหรับเส้นทางที่สมบูรณ์ แหล่งที่มา PlayerData การบังคับใช้ การเริ่มต้น ตัวกำหนดเวลา รายงาน และตารางรหัสการแจ้งเตือน การแยกตารางการค้นหาออกจากกันจะป้องกันไม่ให้หน้าการซ่อมแซมนี้กลายเป็นคู่มือสคีมาที่สอง
